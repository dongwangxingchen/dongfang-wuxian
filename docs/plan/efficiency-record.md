# 效率实测记录（DFW-51 / T12）

> 目的：卡片验收要求"**能用真实记录说明效率提升且回归未漏**"，
> 并明确"历史 17 秒等耗时**不是任何场景的保证**"。
> 所以本文件只记**本机实测数字**，并标注测量条件；不复制历史传闻值。
>
> 测量机器：Mac（16GB 内存，JDK 21，Gradle 9.6，配置缓存开启）
> 记录日期：2026-09-30

## 一、分层验证阶梯（现状实测）

| 档 | 命令 | 实测耗时 | 说明 |
|---|---|---|---|
| **L0** 语法/类型自检 | `:app:compileEmptyDebugJavaWithJavac --offline` | **~2s**（真实重编）<br>~1.2s（无改动，UP-TO-DATE） | 每次编辑后跑 |
| **L1** 单类测试 | `:app:testEmptyDebugUnitTest --offline --tests "<类>"` | **~11s** | 改了某块逻辑后跑 |
| **L1 全量** 宿主测试 | `:app:testEmptyDebugUnitTest --offline` | **~110–160s**（增量） | 改动面广时跑 |
| **L1 全量（强制重编）** | 加 `--rerun-tasks` | **~295s** | 只用于要绝对可信的全新执行 |
| **L3** release 构建 | `:app:assembleEmptyRelease --offline` | **~9–14min** | **仅发版**，日常绝不跑 |

**关键结论**：L0 → L1 → L3 的量级差是 **2s : 11s : 10min**。
日常迭代误跑 L3 是最大的时间浪费（本项目历史教训已写入技能 `dfwx-verify`）。
本轮所有改动都走 L0/L1，只有发版验证才用 L3。

**诚实说明**：上表是**本机当前**数字，不是承诺。
- 增量/全量差别很大（配置缓存、已编译任务数）；
- `--rerun-tasks` 会强制重编全部 213 个任务，所以看起来慢——**这是"全新执行"的代价，不是日常代价**；
- 不同机器、是否首次下载依赖都会显著影响。

## 三、"回归未漏"是怎么保证的（比数字更重要）

本轮新增的每一条守卫都**验过鉴别力**：把对应修复改回去，测试必须变红。
否则就是"写了就绿"的空测试——本项目已多次踩到（例如：
`MemoryLifecycleJvmTest` 第一版因 `App.instance` 为 null 而在空文件上假绿；
`NavBallJvmTest` 第一版因截取窗口越界到隔壁方法而恒真）。

**教训固化为做法**：
1. 源码文本断言必须**按大括号配对取方法体**，不能按固定长度截取；
2. 断言前先确认"前置条件真的成立"（文件真的写了、路径真的对）；
3. 同名字符串在文件里可能多次出现，**必须用签名锚点精确定位**；
4. 不能只测"机制存在"，还要测"**机制被用上**"（接线断言）——
   这一条在 DFW-21（AI 防线接线）、DFW-40（图标负缓存接线）都直接避免了假绿。
