# 需求与独立专题清单

> 每项都是独立研究、制作、用户测试和打磨的完整专题；**不是一次全部开工的清单**。
> 推荐方向可由新证据修正。现状来自本次整理所见的工作树和历史报告，不等于本轮重新验证，更不代表用户已批准制作。
> 本文刻意不指定函数、线程数、缓存期限、动画参数或固定施工顺序；这些由接手模型在当前专题研究后决定。

## 如何使用

选定一个专题后，按 [OPERATING.md](OPERATING.md) 执行。五个要素是：**要达到的体验、已有成果、推荐方向、需要自行研究的内容、用户怎样判断做好了**。每项的正常、失败、恢复、兼容和性能一起考虑，不靠「改了一行」或「编译成功」结案。

历史 T10 只作为搜索/网页需求分组，不再单独开一遍同样的工作；R2 对应 T17，R3 对应 T16，R1/R4/R5/R6 沿用研究报告后期的含义。T1b/T1c 保留历史编号。T2-S/P/K、T3-G、T5-V/N/C 是原有要求的独立入口，不是新增范围；**T5-S（设置界面）和 T5-D（下载界面）是 2026-09-26 用户新点名的独立专题**。

**T20–T24 与 T11-S/B/D/E 是 2026-09-26 只读审计新发现的功能与安全缺口**（证据为文件行号，需在对应专题开工时用当前代码复核）。它们不是用户新提的需求，而是「用户会感知到、但计划此前没覆盖」的方面：工具箱结果出口与个性化、外部分享接入与条目快捷操作、源与优享账号管理、首次启动引导，以及客户端网络安全、云备份、本地凭据与遥测清点。**是否要做、做到什么程度由用户决定**；本清单只保证不遗漏，不代表已批准。其中两项例外属「发布安全」而非可选项：T14 的更新入口死代码、T8 的签名口令回退常量，应在首次对外发包前处置。

原始出处与技术风险统一在 [RISK-REGISTER.md](RISK-REGISTER.md)。完成记录只记到当前专题；跨专题影响标注待回归，不能用一次总验收替代全部体验。

## 一、准备、导航与页面适配

<a id="p00"></a>
### P00｜已有工作保护与开工基线
- **目标**：弄清已有未提交成果，后续改动不覆盖、不重复、不丢失。
- **现状**：导航、解析、更新、测试和文档混在同一工作树，历史验证口径不完全一致。
- **推荐方向**：先确认改动归属、当前可复现状态和可回退边界，不把整理等同于强制提交或清空工作区。
- **自行研究**：只核对与所选专题有关的交叉点；已有证据不足处明确标注。
- **验收**：能说清保留什么、本专题允许动什么、尚缺什么证据；没有覆盖业务文件、泄露凭据或清除数据。见 [准备说明](cards/P00-baseline-freeze.md)。

<a id="t1"></a>
### T1｜悬浮导航的完整体验
- **目标**：去掉底栏，用可拖动、贴边、记忆位置的按钮切换软件库、AI、下载、工具箱、设置；包括 AI 页在内保持常驻，默认右下，不遮挡关键操作。
- **现状**：已有实现与部分真机记录。旧弧形菜单后来因 360dp 重叠、裁切改为竖向胶囊菜单；拖动、重启记忆等整体验收仍需对照当前包。
- **推荐方向**：先保护能用的版本，完善跟手、选中反馈、边界和生命周期，不机械改回早期弧形方案。
- **自行研究**：不同球位、窄屏、键盘、返回和快速切页下的菜单行为；展开状态怎样恢复才不打扰。
- **验收**：五页切换顺手，位置记忆可靠，AI 输入和页面按钮不受遮挡，快速操作没有卡住或残留；用户认可后才进入 RikkaHub 重移植。

<a id="t1b"></a>
### T1b｜导航菜单残留与动画中断
- **目标**：收起、误触、连续点击和切页后不留下无法消失的菜单。
- **现状**：历史记录已有修复及用户真机确认；应保留成果，不凭新计划重做。
- **推荐方向**：把它作为独立回归专题，确认当前导航改动仍维持最终状态一致。
- **自行研究**：只在能复现退化时追查动画中断、触摸取消、页面离开等状态，不预设必须增加更多兜底。
- **验收**：用户原来触发残留的操作及快速反复操作都正常。历史通过不代表未来导航重构可以免测。

<a id="t1c"></a>
### T1c｜全站边距、裁切与窄屏适配
- **目标**：软件库名称不被「黑边」挤压，设置左右留白合理，下载筛选、文件类型胶囊和操作按钮完整可用。
- **现状**：已有下载筛选裁切、按钮挤压和边距不统一的修复记录，不是所有问题都由同一种遮挡造成。**2026-09-26 审计补充：全仓几乎无字体缩放（fontScale）适配——sp 文字放进固定 dp 容器、配合 maxLines 截断，系统大字体下会大面积挤压裁切，风险等级高。**
- **推荐方向**：沿用现有设计基准，先复核真实手机尺寸；不要为统一视觉到处硬改同一个数值。
- **自行研究**：长名称、不同手机宽度和字体缩放、系统栏、空/满列表下的实际边界。
- **验收**：软件库、下载、工具、设置等主页面无裁切、挤压、错位；用户认同整体留白，而不只是截图尺寸对齐。

<a id="t9"></a>
### T9｜全软件预测性返回
- **目标**：侧滑时有正确的返回预览，松手提交、取消复原；网页历史、AI 子页面、独立页面和回桌面均符合直觉。
- **现状**：MainActivity 已有迁移改动；网页返回和 Compose 子栈仍需检查，不能以「有回调」推定视觉合格。
- **推荐方向**：优先系统和 AndroidX 正式机制，保持各页面自己的返回语义，不强行让所有页面共用一段视觉动画。
- **自行研究**：回调启用条件、抽屉/弹窗优先级、网页历史、AI 子路由和系统版本差异；具体 API 以当前依赖为准。
- **验收**：完成与取消手势都不误退、不黑屏、不跳错层；根页能正常交回系统，用户逐类页面实际侧滑确认。

<a id="t24"></a>
### T24｜首次启动与引导
- **目标**：新装首次启动有清楚、可跳过的引导（功能速览、必要权限说明），隐私与数据说明真实可达。
- **现状**：**2026-09-26 审计发现（开工复核）：首启引导弹窗代码从未挂载；「已同意」标记被无条件置为 true，等于首次确认流程从未真正生效。** 权限请求时机分散，参见 T2-P。
- **推荐方向**：先决定是否保留阻断式首启确认，再做视觉与文案；引导密度与 T5-C「少打扰」目标不冲突。
- **验收**：新装首启流程完整、可跳过；升级用户不被重复打扰；文案与实际数据流一致（联动 T4、T11）。

## 二、搜索、目录、图标与软件库

<a id="t6"></a>
### T6｜蓝奏链接与文件夹解析可靠性
- **目标**：正常链接和密码目录可靠打开，浏览、搜索与下载入口不因 App 自身问题把正常源判失效。
- **现状**：已有 UA 被拦、解锁字段不足两类修复和测试记录；历史源数量及可用性不是永久事实。
- **推荐方向**：收尾已有修复并建立代表性回归，保留真实错误分类，不继续盲目换线路、加重试或删源。
- **自行研究**：当前失败样本是网络、限频、验证、密码、页面变更还是确实取消分享；必要时核对真实响应并脱敏。
- **验收**：典型普通/密码/嵌套目录可打开；错误能解释、可恢复；不会因为 App 故障误导用户删除正常源。

<a id="t10-r1"></a>
### T10-R1｜搜索速度、覆盖与真实进度
- **目标**：尽快搜索全部可用软件库并持续给出结果，不长时间停在「3/50 个源·已完成 0·找到 4」。
- **现状**：有进度语义、慢源轮换、压力调节及任务收尾风险线索；尚不能把其中某条静态路径认定为这次真机卡住的唯一根因。
- **推荐方向**：兼顾快速首批、慢源不拖累其他源、完整覆盖和真实反馈；不能只改文案，也不能无限提高并发压垮上游或手机。
- **自行研究**：当前包的源耗时、请求与取消恢复、缓存/索引/网络各自贡献、限频和终态；据数据选择调度策略。
- **验收**：相同条件下有首批时间、持续新增间隔、源覆盖和结束状态的前后对比；慢源失败可见、可恢复，不靠悄悄跳过源伪装提速。

<a id="t17"></a>
### T17｜默认最新排序
- **目标**：**默认最新上传的内容在最上面**，首次呈现与后续新增都遵守同一规则。
- **现状**：历史代码只做文件夹优先，时间字段有缺失和格式差异，流式追加不统一排序。
- **推荐方向**：以真实上传时间倒序为主，稳定处理同时间和未知时间；不要让文件夹优先悄悄盖过「最新在前」。
- **自行研究**：时间含义、精度和可获得比例，未知时间的诚实展示，持续排序与阅读位置保持之间的平衡。
- **验收**：不同到达顺序仍得到一致的最新排序；不伪造日期，不把获取时间冒充上传时间；刷新、返回、继续加载后不乱序或无故跳动。

<a id="t18"></a>
### T18｜搜索结果持续可见与长列表
- **目标**：找到的结果都能访问，持续出结果时不只涨计数、不见内容；结果多也不卡、不无限膨胀。
- **现状**：已有初始 64 条窗口、主要靠滚动扩展及累计追加 View 的线索；它们与调度停滞不是同一个问题。
- **推荐方向**：先分清「结果没有到」与「结果到了未呈现」；平衡增量呈现、滚动位置和资源回收，不预定自动无限扩窗或某一种列表控件。
- **自行研究**：新结果抵达、越过首屏窗口、长时间滚动、返回恢复时的数量一致性和内存/帧表现。
- **验收**：首批之后的所有结果可达，内容更新有反馈，长列表仍流畅；不把「未同时创建全部视图」误判成漏结果。

<a id="t10-r6"></a>
### T10-R6｜搜索框右侧「全部」与筛选入口
- **目标**：右侧入口有真正增量价值，不和下方软件库重复，也不丢失必要的来源范围控制。
- **现状**：现有入口表示自建来源分类；搜索态下方库列表会隐藏，所以不能不查状态就删除。
- **推荐方向**：优先比较「排序放右侧、来源范围在结果区」与其他简洁方案；类型/时间筛选仅在真实数据支持时采用。
- **自行研究**：浏览态与搜索态分别需要什么、现有分类怎样保留、标题缺少扩展名时分类是否可信；给少量视觉方案让用户选。
- **验收**：用户能理解当前排序和范围，轻松恢复全部结果；入口不重复、不误导，已有自建分类不无故丢失。

<a id="t16"></a>
### T16｜图标、头像与缓存可靠性
- **目标**：名称左侧图标和合集头像稳定出现，重进不总等网络，源换图后不会长期显示旧图；加载失败也不空白或串图。
- **现状**：有错误 URL、恢复时不补请求、内存缓存为主及头像回退不当的线索；部分文件夹用本地图标，单个 URL 不是全部问题的根因。**2026-09-26 审计补充：缺自适应图标（无 mipmap-anydpi-v26），桌面图标不随系统蒙版适配；工具箱大量工具共用 20 个 drawable，辨识度低。**
- **推荐方向**：先保证正确地址和请求生命周期，再按实际收益补合理缓存、刷新、失败占位和恢复；不锁死容量或七天期限。
- **自行研究**：真实图片来源、服务端缓存响应、同 URL 换图、进程重启、页面恢复和弱网；避免把普通文件夹图标当合集头像。
- **验收**：首次打开、返回、冷启动、断网重连、源换图都表现合理，无串图；失败可辨认，缓存可更新且存储有界。

<a id="t10-r4"></a>
### T10-R4｜目录下拉刷新与翻页体验
- **目标**：重新设计下拉刷新、加载下一页、失败重试、到底的动画和 UI，解决「加载半天没动静」。
- **现状**：限频等待与实际请求可能共用「正在加载」文案；已有状态和失败提示不足的研究。
- **推荐方向**：让等待、请求、成功、失败、到底各自清楚；保留必要限频，采用有界恢复与直接可用的重试入口。
- **自行研究**：本地追加与网络翻页、刷新和翻页冲突、取消、重复条目、滚动位置、实际延迟来源；不编造百分比或预计秒数。
- **验收**：用户知道现在等什么、失败怎么继续；弱网恢复后不重复、不丢项、不跳回顶部，视觉高级且不过度拖慢加载。

<a id="t10-r5"></a>
### T10-R5｜蓝奏网页页完整体验
- **目标**：网页页美观、好用、适合大众，重要信息看得到；改善顶部「慢慢滑的条」造成的慢感，以及加载、返回、失败和下载操作。
- **现状**：当前是 WebView 加自绘外壳；历史确认 App 没有自绘加载进度条，用户所见条的来源仍需按实际页面辨认。**2026-09-26 审计补充：WebView 的 file 访问与混合内容未显式收紧，重做时按最小权限加固，细节归 T11-S。**
- **推荐方向**：**用户已定：保留 WebView 外壳路线，但整体重做质感**——按 Google 官方审美和现行设计规范重新设计，避免冷硬工具感，重要信息看得到，适合大众使用。
- **自行研究**：动手前先按能力路由选最贴合的设计 Skill；研究真实首屏与视觉等待来源、网页历史、错误恢复、外跳安全、下载入口和独立 Activity 适配；若研究证明 WebView 路线确有无法接受的缺陷，再带证据提出替代方案交用户决定。
- **验收**：加载不靠虚假动画拖时间，失败可重试，返回层级正确，复制/分享/外部打开/下载等原有能力不丢；用户认可完整页面效果。

<a id="t13"></a>
### T13｜失效源识别、提示与反馈
- **目标**：确实取消分享或删除时，清楚告知无法继续下载、建议换其他资源库，并诚恳引导去设置反馈**资源库名字**，便于维护。
- **现状**：底层有部分错误分类，但界面可能把失效语义丢成通用失败；历史曾错误把 App 解析问题说成源失效。
- **推荐方向**：保留原因并给可行动提示；明确区分超时、限频、密码、验证和真正失效。反馈先能用，不必等待整套后台。
- **自行研究**：可靠判据、反馈入口与预填信息、隐私边界和重复反馈；确认失效后的更新/移除清单由用户批准。
- **验收**：正常源不被误删；真正失效提示包含来源与下一步；用户可在设置反馈源名。旧误判下的删除口令不是自动批量删除授权。

<a id="t15"></a>
### T15｜更多可用软件库
- **目标**：继续搜集、去重和接入更多真正可用的软件库，不让「旧源其实没坏」把扩充需求一起取消。
- **现状**：需求独立成立，尚不能用历史源数量宣称本轮已完成扩充。
- **推荐方向**：先复用已有名单，再按需公开检索；以可访问、内容合规、重复率低和可维护为准，不为数量凑源。
- **自行研究**：来源与分享权限、密码、目录/搜索/下载可用性、重复域名及后续维护；后台未建也可研究和整理候选。
- **验收**：给出经验证的新增清单、排除原因与用户确认；入库后手机能正常浏览和使用，不覆盖自建源、不擅自删除旧源。

<a id="t23"></a>
### T23｜软件库源与优享账号管理
- **目标**：已添加的源可编辑（改名、改地址、改密码），不必删了重加；优享账号的登录、切换、退出入口真实可用。
- **现状**：**2026-09-26 审计发现（开工复核）：缺少源编辑能力，改密码只能删除重加且丢历史关联；优享账号管理卡片是从未挂载的死代码，用户无法登录或管理账号。**「移出分类」等操作存在死代码，语义可能与用户理解不一致。**2026-09-26 专项研究（用户质疑必要性，见 [T5-S 研究卡 §8](cards/T5-S-settings-redesign.md)）：优享=蓝奏云优享版（ilanzou.com）会员账号，唯一用途是把分享"转存"到用户自己的优享版网盘，与"下载到本机"完全无关（本机下载不登录也全可用）；设置页卡片是 v1.0.9 有意移除的残留，但目录页「保存到网盘」(:757)与源多选「保存所选源」(:1484)仍是活入口；缺口是登录后无法退出/换账号（验证/移除/多账号仅存在于死卡片）。**
- **推荐方向**：源编辑优先（保留下载历史与分类归属）；优享三选项待用户拍板（整体移除转存 / 保留并补齐账号管理 / 只删死卡片），详见 [T5-S 研究卡 §8](cards/T5-S-settings-redesign.md)。**注意：删除时不得连带删 `showPremiumLoginDialog` 等 9 处活调用链；若整体移除需同步改隐私政策文案。**
- **验收**：编辑源后数据不丢、分类正确；优享登录状态正确显示与切换；不引入绕过上游付费的任何能力。

## 三、全站质感、通知和性能

<a id="t5-v"></a>
### T5-V｜整体视觉、动效与交互质感
- **目标**：软件库、下载、工具、设置和 AI 都稳定顺手、统一而高级，材质、字重、层次、触摸和视觉反馈经得起反复使用。
- **现状**：已有设计 Token、Phosphor 图标及部分页面改造；但这些页面最初是在没有审美 Skill 参与时做的，局部参数一致不代表最终观感一致。**2026-09-26 审计补充：启动首帧窗口底色与系统默认黑存在色差（首帧 #0B0A12），冷启动瞬间有闪变感。**
- **推荐方向**：**用户已定方向——按 Google 官方审美，配合现行设计 Skill 和既有 Token 全面重做**，允许较大幅度改动；先找跨页面最明显的断层，提供少量可视方案；高级不等于堆玻璃、弹跳或延长动画。
- **自行研究**：动手前先按能力路由选最贴合的设计 Skill（Android 原生 View 优先 yan-apple-design），复用既有 Token；研究实际手机上的状态层次、对比、排版、触觉、动画打断与性能；分批推进，不借统一之名一次性全站翻新。
- **验收**：用户认可选定范围的实际质感，正常/空/等待/失败状态协调，操作反馈清楚；不恢复字体切换或违反动效红线。

<a id="t5-s"></a>
### T5-S｜设置界面重新设计
- **目标**：设置页按 Google 官方审美与现行设计规范整体重做，分组、层级、开关、列表、展开动效和质感统一，左右留白与卡片形态协调，不再有"原生默认感"。
- **现状**：历史版本有六分组、折叠动效和卡片样式，但当时没有审美 Skill 参与，观感与细节不到位。**2026-09-26 审计补充（开工先复核）：UA 范围掩码保存时被硬置为「全部」，设置页显示与实际行为不一致；「恢复默认」不彻底（sessionIndexEnabled 两处默认值矛盾、sessionBatchDownloadSingleItem 不重置）；存在从未被调用的重复面板死代码。重做时顺带清账。**
- **推荐方向**：先梳理信息架构和分组归属，再定视觉与动效；复用现有 Token 和 Google 官方思路重排，不靠堆叠材质制造高级感。
- **自行研究**：分组与命名、开关/单选/输入/跳转各类控件形态、展开折叠动效、危险操作确认、设置项搜索、窄屏与长列表、与首页和下载页同一基准。**研究已完成（2026-09-26）：现状、清账清单与方案选项见 [T5-S 研究卡](cards/T5-S-settings-redesign.md)，方向选项待用户拍板。**
- **验收**：用户真机逐项操作，观感高级统一、层级清楚、无裁切错位；设置项不丢失、已保存值和自建源不受影响，恢复默认仍可用。

<a id="t5-d"></a>
### T5-D｜下载界面重新设计
- **目标**：下载页整体重做，任务卡片、进度与速度、状态、筛选、批量操作和空态统一高级，与设置页、软件库保持同一设计语言。
- **现状**：历史修复过筛选裁切和按钮挤压，但整体质感没有按审美规范重做过。**2026-09-26 审计补充（开工先复核）：下载无前台服务/WakeLock/进度通知，App 被系统杀掉后任务静默中断、用户无感知；退出时刷写下载历史最长可阻塞主线程约 4 秒（ANR 风险）；下载历史明文含密码直链、有上限且超限静默丢弃（凭据面见 T11-D）。**
- **推荐方向**：先定信息层级和各状态模型，再重排卡片与操作入口；保留多任务、断点续传、静默安装等既有能力，不做功能倒退。
- **自行研究**：进行中/等待/暂停/失败/完成各态表达、进度与速度呈现、批量选择与删除、与自研通知卡片的一致性、长列表性能、权限与安装提示。
- **验收**：各状态一眼可读可控，单任务与批量操作清楚，长列表流畅；用户认可质感，下载历史和设置不丢。

<a id="t5"></a>
### T5｜全站弹窗治理
- **目标**：弹窗不丑、不偏位、不裁切，不是简单纯黑底白字；所有重要操作可看清、可取消、可完成。
- **现状**：宿主有共享底座，但网页、下载历史、PopupWindow、Compose 等仍有独立实现。
- **推荐方向**：先盘点真实入口与用途，统一设计语义和适配原则；不强求 View 与 Compose 使用同一套实现。
- **自行研究**：长文、列表、输入、键盘、窄屏、返回、遮罩、破坏性确认，以及跨 Activity 的一致性。
- **验收**：逐类真实弹窗在手机上可读、可操作、位置合理；不会挡住输入或误触确认，用户满意而非只验圆角数值。

<a id="t5-n"></a>
### T5-N｜自研通知卡片
- **目标**：采用自研通知卡片，有自己的辨识度；**不能和软件一模一样，也不能脱离整体风格**。
- **现状**：已有 showNotice、toastPanel、下载卡片及 AI 侧提示等不同路径，不能把它们统称为原生 Toast。
- **推荐方向**：建立简洁但有层次的通知语言，区分短提示、结果反馈、下载进度和需行动的错误，先给视觉方案再实施。
- **自行研究**：展示位置、堆叠、时长、打断与关闭、重复合并、键盘和悬浮球避让；不擅自替换有系统义务的通知。
- **验收**：用户一眼懂、不被频繁遮挡；样式独立又协调，连续事件不淹没界面，关键动作可达。

<a id="t5-c"></a>
### T5-C｜多余提示与历史弹窗清理
- **目标**：去掉更新后、下载后等画蛇添足的说明和重复提醒，软件清爽而不漏重要信息。
- **现状**：存在旧 AI 升级一次性提示等历史路径；哪些提示仍必要要核对，不能一律删通知。
- **推荐方向**：按用户价值与出现时机逐项判断，能自然在页面表达的不要反复打断；保留必要错误、安全和破坏性确认。
- **自行研究**：首次/再次启动、升级、下载后、已拒绝提醒后的真实触发；原有「已读」和偏好是否应保留。
- **验收**：用户常用流程不被无用信息打断；有清单解释删除/保留项，不靠清数据重置标记来制造测试通过。

<a id="t7"></a>
### T7｜全软件稳定 60fps 与长期运行
- **目标**：全软件常见交互尽量稳定达到 **60fps**，不是只把一张页面变快；启动、列表、导航、下载、工具、AI、键盘及后台叠加都要覆盖。
- **现状**：有历史性能治理和数值，但不能代表当前混合工作树；同步工作、累计 View、多套线程池、Insets 与生命周期是待测线索。**2026-09-26 审计补充：冷启动主线程同步 IO 偏重（初始化读合集、下载历史 JSON 主线程解析、vendor 启动 runBlocking + 脚本引擎）；无 onTrimMemory 回调，部分长生命周期集合无上限、图标强引用不释放；水平仪等工具切换时旧传感器监听可能滞留。**
- **推荐方向**：在相同设备和场景下测量，按真实瓶颈治理；不预定全换列表、全重写线程池或移除所有动画。
- **自行研究**：帧时间分位、jank、主线程阻塞、内存、ANR/崩溃和长期退化；区分设备/网络条件与 App 可控问题。
- **验收**：有可复现的改前/改后数据和场景清单，主流程无明显卡顿或功能退化；达不到目标的场景如实说明并继续本专题反馈，不用平均帧率掩盖尖峰。

## 四、AI 重移植、输入与内置服务

<a id="t2"></a>
### T2｜RikkaHub 规范重移植
- **目标**：按干净上游与可维护定制重新整理 AI，解决补丁堆积、界面质感、兼容性和难修的问题；不是只换版本号。**用户 2026-09-25 已确认：是"重做一版"，保留 AI 功能，不是删除 AI 入口。**
- **现状**：历史研究以 2.5.4 为目标，但 vendor 并非简单的旧稳定版；实际提交、依赖和补丁需开工重核。
- **推荐方向**：悬浮导航验收后，以可对比、可回退的方式准备干净基线，逐项解释 DFWX 定制去留，尽量保留上游成熟交互，不盲删 vendor；同时按 Google 官方审美重做 AI 页质感。
- **自行研究**：动手前先按能力路由选最贴合的设计 Skill；核对数据/设置迁移、嵌入生命周期、返回、依赖和原生库兼容、补丁重放；绝不能把不安全的共享 key 播种方式照搬回来。
- **验收**：原有已支持 AI 能力与数据不丢，界面和交互获用户认可，定制可追踪；T2-S/P/K 各有明确回归结果，不以编译通过代替整体验收。

<a id="t2-s"></a>
### T2-S｜AI 发消息后切页不断流
- **目标**：发出消息后切去软件库、下载等页，AI 继续回复，回来看到完整内容，而不是切页就取消或丢对话。
- **现状**：旧计划把它并入 T1，且「预判满足/已确认/待验」表述冲突，不能直接认定完成。
- **推荐方向**：以当前实际会话生命周期取证，优先保留成熟生成管线；不无故扩大为杀进程后也永久运行。
- **自行研究**：重复切页、多会话、网络中断、取消回复和 UI 重建，区分应用内切页与系统后台/进程终止的边界。
- **验收**：长回复期间反复切页仍连续，返回内容完整、不重复、不串会话；异常恢复和取消符合用户预期。

<a id="t2-p"></a>
### T2-P｜AI 首次使用权限引导
- **目标**：首次使用把麦克风、相机、通知等必要说明串成清楚的引导，已授权跳过，之后使用不反复被打断。
- **现状**：已有 AiPermissionGate 实现和本地一次性标记；它是体验引导，不是赞助或服务端安全授权。
- **推荐方向**：统一说明后按系统允许的方式逐项请求，拒绝也可进入 AI；不把「一条引导流程」误写成绕过系统弹窗的一键授权。
- **自行研究**：Android 版本差异、拒绝/永久拒绝、后续在功能入口补授权、标记迁移与重复触发。
- **验收**：首次、已授权和拒绝三类用户都能顺利使用应有功能；不强迫无关权限、不循环弹窗，也不把拒绝权限当未赞助。

<a id="t2-k"></a>
### T2-K｜AI 输入框、键盘与边距适配
- **目标**：键盘开关、输入、发送和附件操作自然，输入框不乱跳、不留大空隙、不被遮住；移植后仍稳定。
- **现状**：已有历史修复；Java 宿主与 Compose 同时处理系统栏/IME，不能只改一层就宣布根治。
- **推荐方向**：先复现真实手机问题、厘清两边 Insets 职责，再选最小可维护方案，不继续叠加互相补偿的位移。
- **自行研究**：空态/长对话、键盘反复开关、多行输入、切页返回、手势导航和悬浮球避让。
- **验收**：用户常用键盘与手机上不两段跳、不多吃底边距；输入、发送、返回和附件功能都正常，并有实机效果证据。

<a id="t19"></a>
### T19｜内置共享 AI 密钥真正退出客户端
- **目标**：APK、远程配置和客户端日志/持久化中不携带可复用的上游共享密钥，后台更换密钥不要求用户拿到它。
- **现状**：代码有本地配置读入资源、再播种到 AI 设置的路径；**构建值非空才会把真实 key 打进 APK**。仅发现资源名不能证明既有包内值非空。
- **推荐方向**：内置请求走服务端代理，上游密钥只在服务端；迁移已有客户端残留并评估是否需用户轮换曾外发的共享密钥。自填渠道保持独立。
- **自行研究**：当前包与旧安装残留、代理流式协议、认证/限流/额度/撤销和错误恢复；客户端临时凭证不等同于上游共享 key。
- **验收**：静态产物与运行链路不再把上游共享 key 交给客户端，服务端拒绝滥用；若服务未就绪则安全关闭内置入口，不能带密钥占位发布。疑似已暴露密钥的处置需单独记录。

## 六、后台、维护与交付

<a id="t14"></a>
### T14｜更新检查端到端可靠性
- **目标**：正确识别东方无限的新版本，给出可信下载和安装流程，不因仓库、资产命名或版本比较错误长期报告无更新。
- **现状**：已有改为项目仓库、匹配资产名等修复及单测；镜像端点尚不能假定存在。**2026-09-26 审计发现（高危，开工必先复核）：更新检查入口疑似死代码——`maybeCheckForUpdates` 全仓只有定义处一次命中，从未被调用，意味着用户永远收不到新版本提示；也没有手动"检查更新"入口。** 本专题须先让更新链路真正可达（自动触发时机或手动入口），再谈端到端可靠性。
- **推荐方向**：先验证现有 GitHub 通路、无更新和网络失败；以后后台接入不得破坏这个可用基础。
- **自行研究**：版本比较、资产/签名/完整性检查、允许的下载域名和升级保数据；最终 1.0.0 的兼容方案与 T8 对齐。
- **验收**：有更新、无更新、请求失败、错误资产等状态可信；实际覆盖安装不丢数据，不把上游版本当本项目版本。

<a id="t11"></a>
### T11｜远程后台、AI 服务管理与安全
- **目标**：后台能管理公告、更新、源列表、反馈和内置 AI 服务；安全维护服务器与密钥，而不靠每次发 APK 改配置。
- **现状**：用户没有自己的服务器或域名，`nkbr.cc` 属上游；旧 Cloudflare 方案只是候选，额度、成本、国内访问和合规说法需重查。**2026-09-26 审计补充（开工逐项复核）：vendor 局域网 Web 控制台默认绑定 0.0.0.0、JWT 认证默认关闭且 CORS 放开任意来源；宿主明文流量开关常开且无网络安全配置；云备份规则沿用上游样例，可能把 AI 对话与本地凭据备份出境；Firebase Analytics 仍在依赖树；ADB Shell 工具以英文 success 字样判断命令成功，非英文系统会误判。**
- **推荐方向**：先厘清需要管理的内容和安全边界，再比较少量合适方案；公开配置、管理权限、反馈数据和 AI 代理分别保护，可分阶段但不强制选供应商。
- **自行研究**：容量与费用、访问质量、适用合规、管理认证、最小权限、限流、密钥轮换、备份/回退、配置校验与故障降级；服务端出站 URL 必须校验协议和 host，拒绝 localhost、回环、私有及保留地址，防止请求非授权目标。
- **验收**：用户实际操作关键管理流程，客户端更新可验证/可回退，未授权操作被拒绝；真实上游 key 不下发。不经批准不购买、部署、公开服务或消耗付费额度。

<a id="t11-s"></a>
### T11-S｜客户端网络安全与 WebView 基线
- **目标**：明文流量按需放开而非全局常开，建立网络安全配置；WebView（宿主与 vendor）按最小权限收紧 file 访问与混合内容。
- **现状**：明文流量开关常开且无网络安全配置；WebView file 访问与混合内容未显式设置（2026-09-26 审计，开工复核）。
- **推荐方向**：先盘点真实需要的明文域名，能收紧就收紧；WebView 设置逐项对照官方基线，不凭感觉开关。
- **验收**：蓝奏解析、图片、AI 请求等既有功能不受影响；安全配置有据可查，不留全局明文口子。

<a id="t11-b"></a>
### T11-B｜云备份与数据出境
- **目标**：用户能预期哪些数据会被系统云备份；AI 对话、API key、密码直链等敏感数据不默认出境。
- **现状**：备份规则疑似沿用上游样例；merged manifest 的 allowBackup 最终值需 aapt 核验（2026-09-26 审计）。
- **推荐方向**：定制备份排除清单或按用户决定整体关闭；与 T19、T11-D 的凭据边界一致。
- **验收**：实测或 adb 检查确认实际备份行为；敏感数据不在备份集内，或用户知情选择保留。

<a id="t11-d"></a>
### T11-D｜本地凭据留存与清理
- **目标**：分享密码、密码直链、下载历史中的敏感字段有明确存储边界、可见入口和清理能力；诊断与崩溃记录不携带完整带凭据 URL。
- **现状**：分享密码明文存直链记录且无清除入口；下载历史明文含密码直链；崩溃日志写外部存储、诊断记录可能保存完整 URL（2026-09-26 审计，开工复核）。
- **推荐方向**：先定「哪些可以明文留在本地」，再给用户可见的清理入口；日志与诊断脱敏优先于存储加密。
- **验收**：用户能一键清掉历史里的密码直链；新记录默认脱敏；清理不影响正常下载与源数据。

<a id="t11-e"></a>
### T11-E｜vendor 遥测与依赖面清点
- **目标**：弄清 APK 内有哪些会上报或联网的组件（如 Firebase Analytics），用户知情，能关的关掉。
- **现状**：Firebase Analytics 仍在依赖树；是否初始化、上报什么未确认（2026-09-26 审计）。
- **推荐方向**：逐个清点依赖树里的遥测/统计组件，给出保留、排除或关闭初始化的决定；不引入新依赖。
- **验收**：有清单说明每个组件的用途与处置；处置后 AI 与更新等功能回归正常。

<a id="t12"></a>
### T12｜效率、质量与专业维护方式
- **目标**：更快但不降低质量，让小模型能长期接力；文件和目录命名专业，先查成熟成果，不盲目造轮子。
- **现状**：已有缓存、分层验证和研究归档；历史 17 秒等耗时不是任何场景的保证，也不能因有工具就多开代理。
- **推荐方向**：只读当前专题相关材料，复用已有测试和参考，用适当验证层次减少无用构建；专题内保持小步可回退，跨专题保持单线。
- **自行研究**：实际耗时在哪里、哪些工具确有收益、如何留下最小而足够的批准/证据/反馈记录；不为了命名规范批量改旧文件。
- **验收**：能用真实记录说明效率提升且回归未漏，下一模型知道当前目标、批准范围和未解决反馈；最多 3 个独立子智能体，不把历史「4 个」当新授权。

### T20｜工具箱结果出口与操作便捷性

- **目标**：常用工具好找（收藏/最近使用），图标可辨识，细节行为正确（随机源、判定逻辑、排行来源）。
