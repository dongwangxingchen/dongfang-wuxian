# DFW-147 内置 AI 渠道的防滥用设计

> 2026-10-04 起草。触发事件：内置渠道的应用令牌被写进公开仓库，外部已用脚本直接调用。
> 用户要求：「恢复内置 AI，并且不准再出现会泄露的情况。**让这个 API 离开我们软件就无法使用。**」

## 一、先承认一个事实

**APK 里任何密钥都能被反编译扒出来。** 这是客户端凭据的固有性质，业界没有例外。

所以本设计**不追求"扒不出来"**，而是追求下面三件事：

1. **光有令牌没用** —— 必须能算出签名（抬高门槛）
2. **泄露一个不牵连别人** —— 每台设备独立凭据（可单独封禁）
3. **就算被用也有上限** —— 配额 + 限流（成本可控）

## 二、调研过的方案与取舍

| 方案 | 结论 | 依据 |
|---|---|---|
| **Google Play Integrity** | ❌ **不可用** | 只支持通过 Play 安装、且设备有 Google 服务的应用。本项目是侧载 APK、用户在中国大陆，绝大多数设备没有 GMS。 |
| **Android 硬件密钥认证** | ⚠️ **刻意不采用** | 技术上可用（不依赖 GMS，走 Google 硬件认证根证书链），但：① 已被证实可绕过（泄露的 keybox、远程真机代理）；② 模拟器 / 部分机型 / 自定义 ROM 不支持 —— 会把正常用户挡在门外；③ 证书链 + 吊销校验的维护成本高，Google 根证书轮换时会连带出问题。**风险大于收益。** |
| **请求签名（HMAC）** | ✅ **采用** | 所有设备都能用，零兼容风险，实现简单，可长期维护。 |
| **每设备独立凭据** | ✅ **采用** | 泄露一个不影响别人，且能单独封禁。 |
| **配额 + 限流** | ✅ **采用** | 让损失有绝对上限 —— 这是最后一道、也是最可靠的一道防线。 |

## 三、分层设计

### 第 1 层：请求签名

App 对每个 AI 请求附加三个头：

```
X-DFWX-Ts:    <Unix 秒>
X-DFWX-Nonce: <随机十六进制，每次请求都不同>
X-DFWX-Sig:   <HMAC-SHA256(signKey, ts + "\n" + nonce + "\n" + sha256(body))>
```

服务端校验：

- `ts` 与服务器时间相差不超过 **120 秒**（防重放）
- `nonce` 在时间窗内**未被用过**（内存集合，防同窗重放）
- 签名正确

**效果**：只拿到令牌的脚本 → 401。必须反编译出签名密钥、并重新实现签名算法才能用。

### 第 2 层：每设备凭据

- App 首次启动生成一个随机 `installId`，向服务端注册，拿到本机专属凭据
- 所有请求用本机凭据
- **服务端可以只封禁某一台设备，不影响其他人**

### 第 3 层：配额

- 每台设备每日请求数硬上限
- 超出 → 返回明确的错误，App 提示"今日额度用完，可在设置里配置自己的渠道"

### 第 4 层：监控

- 异常（某设备/某 IP 突增、401 突增）写日志并告警

## 四、实施顺序（避免把用户挡在门外）

**关键风险**：签名一旦出问题，App 直接不能聊天。所以**分两步上线**：

1. **观察模式**：服务端只校验、只记录，**不拦截**。跑一段时间确认 App 侧签名正确率 100%。
2. **强制模式**：确认无误后再开启拦截。

这样任何签名 bug 都会先被发现，而不是直接让用户用不了。

## 五、密钥管理

- **签名密钥不进仓库**：和令牌一样，从 `local.properties` / 环境变量读，构建期注入
- 服务端密钥在 `/etc/nginx/dfwx-ai-secret.conf`（600，root）
- **轮换**：改服务端 + 发新版；服务端支持**同时接受新旧两个密钥**，给老版本留过渡期
- 机械守卫测试：仓库里出现密钥形态的字符串就变红（已有 `repoMustNotContainTheBuiltInToken`，扩展覆盖签名密钥）
