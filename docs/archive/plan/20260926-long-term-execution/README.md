## 1. 核心约定

**每个要求都按一个完整专题来做：研究 → 用户批准 → 制作与自测 → 停下来让用户测试 → 根据反馈继续打磨 → 用户认可后收尾。进入下一个专题仍需用户同意。**

- 「大任务」指把这个体验及其正常、异常、恢复和验证做完整，不是顺手修一行就结案，也不是趁机扩大成全仓重构。
- 规划负责记住目标、边界、现状和推荐方向；后续小模型负责专题内的具体研究、方案取舍与验证。
- **技术建议可以、也应该被证据推翻。** 不必因为是强模型写的就服从；发现错误要给出证据，修正当前专题记录并说明影响。
- 产品要求和安全边界不能偷偷改。改变用户已定的体验、成本、数据处理或工作范围，仍要由用户决定。
- 一次只推进一个专题。同专题可分阶段、小步实现；自测通过只是「待用户测试」，不是「用户已满意」。
- 用户暂时没有反馈时，保存检查点并停止；不自动补做下一个专题，不因「顺手」改动相邻功能。

## 4. 优先方向与必要关联

**推荐先保护和收尾已有成果，再解决搜索/浏览的核心痛点。** 已有研究不能代替开工时的验证；用户可以选择当前最痛的一项，不需要按整张表排队。

- 开始改业务前先做 P00，确认重叠改动与回退边界；不要求先提交所有文件。
- 保留用户已定的先后关系：**悬浮导航完成验收后，再做 RikkaHub 重移植**。AI 切页、权限、键盘各有独立验收，不能被「重移植编译过了」吞掉。
- **全站质感重做是用户明确的大方向**：设置页、下载页、软件库、蓝奏网页等都要按 Google 官方审美与现行设计 Skill/规范重新设计，不是只修个别控件。历史页面是在没有审美 Skill 参与时做的，允许较大幅度重做；仍按专题分批推进，一次一个，避免一次性全站翻新无法验收。
- 交付方式：**测试版走 GitHub（与历史做法一致），不直接把 APK 装进用户手机**。需要手机实测时先汇报进度并请示，用户同意后再操作，且不要太频繁；理论上做到足够好再请用户测试。
- 搜索速度、排序、列表呈现是不同问题。可先解决当前最影响使用的一项；另一专题的整体重构不应成为无理由的前置条件。
- 目录、网页、失效源、弹窗需要统一错误语义，但**不互相等待全部完成**。当前专题若必须触及共享部分，只处理其必要范围并记录后续回归。
- 性能基线是每个相关专题的验证准备，不必等 T7 全站治理完成才开工；T7 最后还需覆盖跨页面和后台叠加场景。
- AI 重移植、内置渠道权限与后台需先厘清接口边界，但不互相要求「整个项目先做完」。T19 可先移除客户端共享密钥通路并安全关闭尚未接通的内置服务；**恢复内置服务前，服务端代理和防滥用验证必须就绪**。
- 赞助页排版、关于页和一般 UI 不必等整套后台完成；没有付费基础设施的批准，不购买、不部署、不承诺免费额度。
- T8 提供每个专题的真机预览与安全交付要求；**每次预览不等于公开发布**。全部专题不必完成才让用户试用，正式发布仍需单独批准。

遇到真实依赖时，说明「缺少什么、影响什么、最小可行边界是什么」。需要换专题或扩大范围就停下交用户决定，不把依赖写成循环，也不悄悄并行开工。

### 推荐推进顺序（建议，非强制）

**用户已拍板（2026-09-26）**：审美线打头，第一项 = **T5-S 设置界面重做**，之后按下面顺序走；研究先行——T5-S 的研究结论与方案选项先交用户讨论拍板，才动代码。另经用户同意：**签名口令回退清理（T8 范畴）与 T14 更新入口修复**不占独立专题，在**第一次发 GitHub 测试包之前**顺手处置。

下面的顺序只是当前推荐的推进路径，理由写在各条后面；用户随时可以指定别的起点，后续模型也可凭新证据调整。

1. **P00 基线保护**（只读、快）——先弄清已有改动和回退边界，之后每个专题才敢动文件。
2. **T5-S 设置界面重做**——控件类型最全（开关、单选、输入、跳转、折叠、危险确认），先做它能一次定下全站复用的新组件语言，后面下载页、网页页直接沿用，避免同一套语言发明三遍。
3. **T5-D 下载界面重做**——复用第 2 步定下的组件与状态表达，用户高频页面。
4. **T10-R5 蓝奏网页页重做**——复用同一套语言，独立 Activity，风险中等，适合在语言定稿后做。
5. **T17 最新排序 + T16 图标与缓存**——功能痛点，独立于审美线，做完用户能立刻感到搜索变好。
6. **T18 长列表呈现 → T10-R1 搜索速度与覆盖 → T10-R6 右侧入口**——搜索核心，按「先看清再加速」的顺序做。
7. **T1/T1b 剩余验收 → T2 RikkaHub 重移植（含 T2-S/P/K）**——导航外壳定稿后再换 AI，避免返工。
8. **T13 失效源 / T15 扩充软件库 → T5 弹窗 / T5-N 通知卡片 / T5-C 多余提示 → T3 赞助 / T3-G 渠道边界 / T4 关于页**。
9. **T19 密钥退出客户端 / T11 后台 → T7 全站性能 → T8 正式发布**。

**取舍提示**：如果搜索卡顿比观感更影响你使用，可以把第 5、6 步提到第 2 步前面，审美线整体后移。两条线互不阻塞，但**不要同时开两个专题**。

**审计新发现的位置**：T20–T24 与 T11-S/B/D/E 默认不进推荐顺序，属独立小切口，用户可随时点名插队。唯二例外是发布安全项：**T14 的更新入口死代码**（想让测试包给出更新提示，就得先让链路可达）与 **T8 的签名口令回退常量**（首次对外发包前必须处置）。

**手机测试节奏**：T1 的剩余验收项已经实现，不需要额外开发，可以搭第一次 GitHub 测试包一起确认，不单独占用一轮；其余专题同理，先把自测做到位，再一次性请用户配合。

## 6. 共同边界

- 新业务修改先有该专题的用户批准；批准计划整理不等于批准编码、提交、推送、部署或发布。
- 保护原有未提交工作；删除、清数据、卸载、覆盖备份等必须明确授权。`<本地目录>/_<本地加密备份>/` 与桌面<本地备份> **勿删勿动**。
- 不读出或传播 `local.properties` 内的凭据；签名密码、共享 AI key、Token、Cookie 不进文档、日志、代码、脚本或提交。审计结果也须脱敏。
- 内置上游共享密钥不进入 APK，也不远程下发给客户端；改为服务器代请求。用户自填渠道仍保持独立，不因内置服务迁移被强制走用户的后台。
- 宿主区保持 Java 程序化 View，未经批准不加第三方依赖；vendor 按上游 catalog 和 DFWX PATCH 规则维护，不能盲删目录或把旧补丁全部照搬。
- 图标沿用 Phosphor SVG 转换；不恢复已删的字体切换，不引入 SF Symbols。交互动效遵守现行 VPA/直接属性规则，禁止重新引入 `dynamicanimation`；不因旧文件批准过就恢复物理弹簧。
