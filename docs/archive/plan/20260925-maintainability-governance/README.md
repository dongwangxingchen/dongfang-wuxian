> 状态：G0 文档基线
> 适用根目录：`/Users/lishaowei/heiyao/src`
> 当前基线：分支 `test`，HEAD `30af1f0`（v1.22.4）
>
> 这不是“所有问题已经修好”的证明，也不是把旧计划自动升级成命令。本包的作用是把当前证据、风险、目标架构、质量门禁和后续任务固定下来，让后续修改可以验证、回退和交接。

## 1. 这套治理包解决什么

东方无限同时包含：

- 宿主 Java 程序化 View：蓝奏云、软件库、下载、工具箱、设置、ADB 和更新；
- `rikkahub/` vendor：Kotlin、Compose、AI 对话和上游能力；
- Gradle、Manifest、CI、发布和 AGPL 合规链；
- 大量历史专题计划、研究报告和未跟踪文档。

治理目标不是把所有文件重写，而是：

1. 先保护发布、下载、安装、凭据和用户数据边界；
2. 再补齐关键状态机和生命周期测试；
3. 按领域渐进拆分超大宿主类；
4. 让宿主 UI、Compose UI、交互动画和性能有统一证据；
5. 让依赖、vendor 补丁、CI 和发布可追溯；
6. 让后续轻量模型可以只接手一个小任务，而不是猜整个项目。

## 2. 证据优先级

发生冲突时按下面顺序判断：

1. 当前工作树的源码、配置和构建产物；
2. 当前命令输出、测试、真机/模拟器实测；
3. 当前项目规范：`AGENTS.md`、发布 Skill 和用户最新明确决定；
4. 本治理包中已附证据的结论；
5. 既有 `docs/plan/`、`docs/tasks/` 和历史研究；
6. 旧模型推测、旧截图、旧版本行号和“已完成”标签。

旧文档不会因为写得详细就自动正确。新证据推翻旧结论时，更新风险台账和任务卡，并记录“原判断—新证据—新结论”。

## 3. 用户已确认的产品边界

- 先落盘治理包，再进入源码整改。
- 外部 Intent 下载保留，但安装必须强制用户确认；外部输入不得直接触发自动安装或 Shizuku 静默安装。
- 当前内置 AI 模型和内置渠道直接移除；不再采用“保留内置渠道、让用户填写 Key”的过渡方案。不得误删用户自行创建的 Provider。
- 普通外部 AI/API 地址只允许 HTTPS；未来若需要本机服务，loopback 例外必须单独研究、单独测试和单独记录。
- 只测手机，手表测试永久停止。
- 宿主区不随意引入第三方依赖；动画方案必须先研究现有批准能力和本地参考，不为单个控件制造割裂特例。
- 发布、推送、安装用户手机、清数据、删除文件和修改凭据仍遵守项目红线。
