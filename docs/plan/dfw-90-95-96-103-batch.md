> 每项都写了**根因证据**，不是"看着像所以改了"。

## ① DFW-90 更新机制解耦：后台改版本号就能推送

**用户原话**：「你刚刚跟我说的，必须得出个 1.0.6 版本的包才能更新，但是我不希望这样。
我希望的是，只要我在后台改了当前版本，版本号比软件的版本号大，那它就会推送我的下载链接。」

### 装包前的四道校验，各自的作用

| 校验 | 作用 | 处理 |
|---|---|---|
| 包名一致 | 确认这确实是《东方无限》 | **留** |
| 签名一致 | 确认是作者自己打的包，不是别人塞的病毒 | **必须留** |
| 版本名一字不差 | 后台写的必须和包里写的一模一样 | **删**（就是它最烦） |
| 真实版本序号更大 | 确认包真的比用户手上的新 | **留**（报错改成人话） |

**为什么"真实版本序号"这条不能一起删**：后台填的版本号只决定「要不要提醒更新」，
用户真正装上的还是那个包。包本身不比当前版本新 → 装完版本没变 → 后台还说有新版本
→ **无限循环提示**。这是物理限制，不是保守。

顺带把版本名的格式校验从"必须严格 `x.y.z`"放宽成"非空 + 过滤文件名非法字符"：
后台控制台对版本名**没有格式校验**，用户填个 `1.0.24-beta` 就会让所有用户收不到更新，
而报错只有一句"版本信息无效"，极难排查。去掉第 ④ 条后 `version` 只剩一个用途：拼临时文件名。

守卫：`UpdateVerificationPolicyJvmTest`（6 例，3 条反向探针实测变红）。

## ② DFW-96 搜索提速：全局搜索每个源最多 3 页

**用户反馈**：「搜索速度还是太慢」→ 追问后明确「**全部搜完要等太久**」→ 选项里选了 A（每源 3 页）。

### 根因（都是实测出来的行号，不是猜）

| 事实 | 出处 |
|---|---|
| 全局搜索原来复用 `sessionSearchMaxPages`，默认 0 被当成 **1000 页** | `LanzouCore.java:393` |
| 同域名每页至少间隔 **1100ms** | `LanzouCore.java:62` `ORIGIN_PAGE_SLOT_MS` |
| 开了文件夹递归后每个子文件夹再翻一遍 | `LanzouCore.java:1558-1573` |
| 搜索总预算 **180 秒** | `LanzouCore.java:86` `DEFAULT_SEARCH_BUDGET_MS` |

所以"跑满 3 分钟"是常态。搜索是"找东西"，不是"备份整个目录"：
前 3 页（约 150 条/源）足够命中绝大多数目标。

### 关键：**没有把单源搜索一起砍了**

`sessionSearchMaxPages` 在界面上叫「**单源翻页**」（`perfTierFacts`），本意是
"点进一个源之后能翻多深"。用户抱怨的是全局搜索，单源深挖是他自己主动缩小的范围，
一起砍掉就是**用户没要求过的功能回退**。所以拆成两个独立预算：
`SEARCH_MAX_PAGES_GLOBAL=3` 只管全局，单源走原来的设置。

卡里的红线「搜索必须仍然**覆盖全部源**」不受影响 —— 源一个不少，只是每个源不再翻到底。

守卫：`SearchPageBudgetJvmTest`（4 例，反向探针 2 条变红）。

## ③ DFW-95 搜索页：底部黑色留白 + 返回无动画

**用户原话**：「搜索页面搜索后，**底部出现了黑色留白，很丑**」
「而且从搜索界面，我如果使用了安卓的返回，它**没有任何的动画效果**……我希望你可以修复一下，
给它加个，比如什么动画效果吧。渐隐啥的。」

### 留白：**先量再改**，不靠猜

用 `@GraphicsMode(NATIVE)` 把页面渲染成 PNG、逐行扫像素定位（视口 1078×2338 @2.625）：

| | 结果区最后一行 | 下方空白 |
|---|---|---|
| 改前 | y=2119 | **218px（83dp）** |
| 改后 | y=2214 | 123px（大部分是最后一行卡片的下边距） |

布局实测指出根因：`homeHistoryH()` 写的是 `vh - dp(64)`，注释说「64=框52+间距12」——
但搜索框与间距是 `homeScroll` 的**兄弟节点**（实测：框 0..137px、间距 137..169px、
`homeScroll` 从 169px 才开始），本来就在滚动区外面。
**再扣一次 64dp，等于在搜索页底部永久挖掉 64dp，任何内容都到不了那里。**

**过程中排除掉的两个错误假设**（都写下来，免得后人重走）：
1. "窗口化渲染被截断" —— 实测**不成立**：模拟滚到底，`searchWindowTarget` 64→128→192，
   渲染格数同步增长，v1.19.4 已经修好了。
2. "64dp 是可见的色带" —— 实测**不成立**：`homeHistory` / `homeColumn` / `homeScroll`
   都没设背景色，全是透明（黑对黑）。所以问题是"**内容永远到不了那一块**"，不是"颜色不对"。

### 返回动画

`exitHomeSearchFocus()` 原来直接把两个 View 的可见性一开一关（硬切）。
现在走全站现成的**原位交叉淡化**，节奏与曲线照抄 `transitionSourceFilter`：
退 `DUR_EXIT_FAST`(100ms) → 换内容 → 进 `DUR_SMALL`(150ms)，曲线 `standardEase()`。
**不另发明数值** —— 触摸路径全程 VPA ≤ 300ms 是全站铁律。

**先退后进、而不是同时交叉**：两者是同一个 LinearLayout 里的兄弟节点，
同时可见会让列表高度瞬间叠加、滚动位置跳一下。

进出两个方向都做了（对称）。

守卫：`SearchPageBottomAndBackJvmTest`（5 例，含真布局测量 + 反向探针 2 条变红）。

## ④ DFW-103 公告弹窗秒弹

**用户反馈**：「公告弹窗弹出太慢。」

### 根因
`maybeFetchNotices()` 启动后**先发一次完整网络请求，拿到数据才弹**，
而且**没有任何本地缓存**，每次都是现拉。超时是连接 6s + 读取 8s —— 最坏 **14 秒**。

### 修法
1. 把上一次成功拉到的**四个集合的原始 JSON** 存盘；启动时先用它渲染并弹窗（**零延迟**），
   网络回来再覆盖。存原始 JSON 而不是解析后的对象，是为了还原时**复用同一套解析器**，
   否则会出现"缓存格式和线上格式不一致"这种只在离线路径才炸的坑。
2. 超时 6+8 → **3+4 秒**（服务器在国内，几百字节的 JSON 用不了那么久；
   宁可早点失败不打扰，也不让用户干等）。
3. 启动现在会**两次**走到 `maybePopupNotices`（先缓存、后网络），
   所以按 id 去重，否则用户会看到**两个叠在一起的公告对话框**。

### 过程中自己写出来又修掉的一个真 bug
第一版把 `sink.notice` 直接传进 `parseNotices(...)`。正常路径是 `fetch()` → `fetch(null)`，
此时 `sink` 是 null → **NPE**，而它被外面那圈 `catch (Exception ignored)` **静默吞掉** ——
表现为"公告和更新记录永远拉不到，日志里一个字都没有"。
改成局部变量接住，并加回归守卫 `fetchMustNotDereferenceTheNullableSink`。

守卫：`NoticeSnapshotCacheJvmTest`（8 例，走真实 SharedPreferences + 真实解析器，
3 条反向探针实测 6 个用例变红）。
