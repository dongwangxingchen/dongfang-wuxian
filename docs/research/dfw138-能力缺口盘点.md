## 二、新获得的能力：证明「我的修复真的打进 APK 了」

以前打完包只验三样：包名、版本号、ABI。**「我的代码改进去了吗」从来没验过。**

现在能验了。方法是把 APK 里的 `classes*.dex` 抠出来按字节搜。

### ⚠️ 踩到的坑

| 工具 | 结果 | 原因 |
|---|---|---|
| `grep "中文"` | ❌ 全部找不到 | grep 默认跳过二进制文件 |
| `grep -a "中文"` | ❌ 还是找不到 | DEX 里字符串是 **MUTF-8**，多字节序列被当成非文本 |
| `strings` | ❌ 找不到 | 同上，`strings` 只认连续可打印 ASCII |
| **Python 按字节搜** | ✅ **全部命中** | `'中文'.encode('utf-8') in dex_bytes` |

MUTF-8 对**中文（BMP 字符）**和 UTF-8 是**逐字节相同**的，所以 Python 直接搜就行。

### 实测结果（对 `20261004-005409` 那个包）

| 内容 | 在不在包里 |
|---|---|
| `不是这个源坏了`（DFW-36 新文案） | ✅ |
| `蓝奏换了链接地址` | ✅ |
| `源异常：` / `已下载` | ✅ |
| `failedSourceSuffix`（方法名） | ✅ |
| `flashDownloadSummary` | ❌ **正常**——R8 把只调用一次的私有方法内联了 |

**结论：包是新的，修复确实进去了。** 方法名找不到不等于没进去，要区分「被内联」和「没编译进去」。

## 三、好消息：崩溃日志一直是可读的

一直担心 release 包混淆后，用户发来的崩溃日志是 `a.b.c` 这种乱码。**实测证明没有。**

`app/proguard-rules.pro:11` 写着 **`-dontobfuscate`**（故意的）。验证：

```
没改名的类: 17,601
改了名的类:  2,141   ← 全部是 R8$$REMOVED$$CLASS$$N
真正的改名:      0   ← 一个都没有
```

那 2,141 个是 **R8 删掉的无用库类**（`androidx.compose.*`、`androidx.camera.*`、`com.google.android.*`），
不是改名。所以：

- ✅ 用户发来的崩溃日志**类名方法名都是真的**，DFW-101 那套一直有效
- ✅ `retrace` 工具也在（`~/Library/Android/sdk/cmdline-tools/latest/bin/retrace`），但**用不上**
- ⚠️ 副作用：APK 反编译后源码基本可读。本项目 AGPL 开源，无所谓

## 四、确认的缺口（按严重度）

| # | 缺口 | 严重度 | 补法 | 成本 |
|---|---|---|---|---|
| 1 | **Web 控制台从没真跑过** | 高 | Playwright headless Chromium | 281 MB 磁盘 |
| 2 | 跑不了真机 / 模拟器 | 高 | ❌ 内存不够（见下） | — |
| 3 | UI 回归靠人眼看两张图 | 中 | Roborazzi（带 AI 视觉断言） | 一个 Gradle 依赖 |
| 4 | **Serena 不支持 Java** | 中 | 配 JDTLS（本机有 JDK 21） | 改配置 |
| 5 | 性能 / 内存泄漏测不了 | 低 | 需要设备 | — |

### 缺口的证据

**① Web 控制台**——我自己写的测试文件开头就承认了：

> 控制台是一整个 index.html 里的内联脚本，没有模块边界，平时只能靠"打开浏览器点一点"来验证。

而 `server/dfwx-admin/index.html` 我改过多次（网盘板块、http 地址），**一次都没真渲染过**。
现有 `pan_render_test.mjs` 是拿正则匹配源码，**不是真渲染**。

**④ Serena**——实测报错：

```
Cannot extract symbols from file .../MainActivity.java. Active languages: ['kotlin']
```

Serena 走 LSP，Java 要挂 JDTLS。本机 JDK 21 在（`~/sdk/jdk-21.0.11.jdk`），是配置问题不是能力问题。

**② 模拟器**——实测这台机器：

```
真正空闲内存:      0.1 GB
可回收(inactive):  3.2 GB
已经在换页:        pageouts 33617
```

模拟器至少要 2–4 GB。而且 `AGENTS.md` 明确写过「gradle 与设备截图严禁并行（CPU 饥饿会让
SystemUI ANR 污染证据）」。**结论：不装。**

## 五、顺手发现的结构问题

`MainActivity.java` 是 **5,731 行的巨型类**，而且连接度极高：

| 方法 | 调用它的地方 |
|---|---|
| `showNotice` | **134 个** |
| `showTopBanner` | 5 |
| `failedSourceSuffix`（我新加的） | 5 |

这解释了为什么改一个方法会波及 237 个符号。这是 DFW-29（拆分 MainActivity）该存在的理由，
但**不是现在的重点**——先把门面发了。
