## 2. 截图：四种真实排版（每种都有出处，可照抄）

### A. 单行流式 + 固定像素宽 + 点击看大图 —— NewPipe（39.8k）

```markdown
[<img src="fastlane/.../00.png" width=160>](fastlane/.../00.png)
[<img src="fastlane/.../01.png" width=160>](fastlane/.../01.png)
... ×9
<br/><br/>
[<img src=".../09.png" width=405>](.../09.png)   ← 平板图单独一行，更宽
```
- **9 张手机图 `width=160`**，每张**同时是链接**（点开看原图）；用 `<br/><br/>` 强制换行再放 2 张平板图。
- 出处：`TeamNewPipe/NewPipe` README `## Screenshots`（第 34-47 行）。
- 为什么有效：不写 `<table>` 也能自然折行，窄屏/宽屏都不裂；160px ≈ 手机 1/6 宽，一行能排 6-8 张，
  **"功能很多"一眼看得出来**，但不占垂直空间。

### B. 百分比宽 + 三张一行 —— MaterialFiles（9.1k）

```html
<p><img src=".../1.png" width="32%" /> <img src=".../2.png" width="32%" /> <img src=".../3.png" width="32%" />
<img src=".../4.png" width="32%" /> ... </p>
```
- **6 张，`width="32%"`**，用 `<p>` 包住两行（3+3）。
- 出处：`zhanghai/MaterialFiles` README `## Preview`（第 15-16 行）。
- 为什么有效：**百分比**随窗口自适应，不会在小窗口里挤压；三列是"手机截图 + 并排"的甜点值。

### C. Markdown 表格 + `alt` 当图注 —— Obtainium（20.2k）

```markdown
| <img src="./assets/screenshots/1.apps.png" alt="Apps Page" /> | <img src=".../2.dark_theme.png" alt="Dark Theme" /> | <img src=".../3.material_you.png" alt="Material You" /> |
| --- | --- | --- |
| <img src=".../4.app.png" alt="App Page" /> | <img src=".../5.app_opts.png" alt="App Options" /> | <img src=".../6.app_webview.png" alt="App Web View" /> |
```
- **6 张，三列两行，每张用 `alt` 文字当图注**。
- 出处：`ImranR98/Obtainium` README `## Screenshots`（第 90-94 行）。
- 为什么有效：**唯一能带图注的做法**（Markdown 原生不支持图注）。想让人看懂"这是深色主题""这是应用详情页"就用这种。

### D. 居中块 + 两张不同宽度 —— rikkahub（8.0k，**本项目上游**）

```html
<div align="center">
  <img src="docs/img/chat.png" alt="Chat Interface" width="150" />
  <img src="docs/img/desktop.png" alt="Models Picker" width="450" />
</div>
```
- 出处：`re-ovo/rikkahub` README 第 17-20 行；同文件第 1-13 行还有
  `<div align="center">` + 图标 `width="100"` + `<h1>` 标题 + 徽章 + 标语 + Discord 的**居中头部块**。
- 为什么有效：手机图（150）和平板/桌面图（450）**并排**，一张竖一张横，信息密度高且不打架。

### 尺寸统计（10 个仓库、全部内联宽度，共 **49** 处）

| 宽度 | 出现次数 | 典型用途 |
|---|---|---|
| `160` | 9 | 手机截图（NewPipe 全家） |
| `275` | 6 | 手机截图（AnkiDroid） |
| `32%` | 6 | 手机截图三列一行（MaterialFiles） |
| `25%` | 4 | 四列 |
| `50` | 5 | 赞助商 logo / 头像 |
| `150` / `240` / `405` | 2 / 3 / 2 | 手机 / 中图 / 平板横图 |

**结论：手机截图用 `width=160`（或 `25%`/`32%`），平板横图用 `405`。不要用 Markdown `![]()` 直接贴原图**——
**真正展示截图的 8 个仓库里有 6 个（75%）用带 `width=` 的 HTML `<img>`**
（NewPipe / AnkiDroid / rikkahub / Android-DataBackup / MaterialFiles，以及 Obtainium 用 `<img>` 不带宽度），
只有 2 个纯用 Markdown（v2rayNG、legado），Shizuku 完全不放图。
带 `width` 属性的图片共 **49 处**。原因很实际：**原图按 1080 宽渲染会占满整页**。

## 3. 下载入口：怎么放才显眼（四种做法，按显眼度排序）

| 做法 | 样本 | 原文/形态 | 评价 |
|---|---|---|---|
| ① 醒目独立节 + 纯链接 | v2rayNG | `## Download / 下载` → 一行裸 URL `[https://github.com/2dust/v2rayNG/releases](...)` | **最稳**：链接文字就是完整 URL，用户能直接读、能复制、不怕点错 |
| ② 多行链接 + 推荐标注 | rikkahub | `## 🚀 Download` → `🔗 [Download from Website](...) (Recommended)` + Play 链接 | 有多个来源时最清楚 |
| ③ 徽章兼作按钮 | v2rayNG | `[![GitHub Releases](https://img.shields.io/github/downloads/.../total?logo=github)](releases)` | **显眼但语义模糊**：它显示的是"下载总量"，不是"下载"按钮 |
| ④ 编号安装步骤 | NewPipe | 5 种安装方式编号列出，**并说明签名密钥是否一致** | 教程级，适合"安装有坑"的项目 |

**关键事实：GitHub README 根本没有真正的"按钮"**——只能靠 badge / 图片 / 链接。
想要"像按钮"，行业做法就是 ① 或 ③。**对东方无限，推荐 ①（一个 `## 下载` 节 + 一行裸 URL），
再加一个 Release 徽章当"最新版本号"的可视指示**（但见 §4：得先让那个徽章显示版本号而不是 test tag）。

## 4. 徽章：放几个才不堆砌

**数据**：0 个徽章的有 5 个（含 47.1k 的 legado、39.8k 的 NewPipe、31k 的 Shizuku）；
4 个的是 termux；6-7 个的是 v2rayNG 与 Android-DataBackup。

**推荐 3 个，且必须"每个都回答一个用户会问的问题"**：

| 徽章 | 回答什么问题 | 现状 |
|---|---|---|
| License（AGPL-3.0） | 「我能拿去改吗」 | ✅ 已有，实测渲染 `license: AGPL-3.0` |
| Release | 「最新版是几」 | ⚠️ 已有但渲染成 `test-20261004-02`，**需修** |
| Platform（Android 8.0+ / arm64-v8a） | 「我的手机能装吗」 | ✅ 已有 |

**明确不要加的**：commit 活跃度、CodeFactor/代码质量分、star 数、last-commit、
"Powered by"、深链 AI 徽章（`Ask DeepWiki`——那是给有 wiki 的项目用的，本项目没有）。
理由：v2rayNG 放了 6 个（含 CodeFactor、commit activity），但它的 star 并不比 0 徽章的 NewPipe 高，
**这些徽章对用户决策零帮助**，只是维护者自嗨。

## 5. 安装说明写到什么颗粒度

三档真实样本：

| 档 | 样本 | 写到什么程度 |
|---|---|---|
| 轻 | rikkahub | 只给下载链接，不解释安装 |
| **中（推荐）** | NewPipe | 编号列出安装方式；**明确说"对比签名密钥"**；说明不同来源的包能否互相覆盖安装 |
| 重 | termux | 整节讲清 sharedUserId、签名不一致会报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`、要先卸载 |

**对东方无限的判断：必须写到"中"档**，而且有两个**本项目的特殊坑必须写**（都是真实踩过的）：
1. **「允许安装未知来源」**——不走应用商店，用户第一次装一定会遇到。NewPipe/Obtainium 都没写这句
   （它们的用户群是极客），但**东方无限的用户是普通中文用户**，必须写一句。
2. **arm64-v8a**——`README.md:88` 已写「面向手机（arm64-v8a）」，但没告诉用户"装不上"时怎么判断。
   建议补一句「老设备/32 位机型装不上是正常的」。
3. **覆盖安装的 versionCode 规则**（若采用路线 B 的编号重置）——首版要求卸载重装，属于"不写用户一定会来问"的事。

**不要写**：Gradle 构建参数（那是开发者章节的事，别混在用户安装里）。

## 6. 要不要 FAQ

**10 个里只有 2 个有 FAQ**（termux、NewPipe），且都是**链接到 wiki**，不是写在 README 里。
Obtainium 用一个 `## Limitations`（局限说明）代替 FAQ。
rikkahub / v2rayNG 用 **GitHub 新版 alert 语法**做"就地提示"：
`> [!WARNING]`（rikkahub 警告山寨 fork）、`> [!TIP]`（v2rayNG 提示电脑版在别处）。
10 个仓库里只有 2 个用了 alert，`<details>` 折叠只有 termux 用。

**推荐**：**不写独立 FAQ 节**，改用 3 个就地提示（更短、更可能被读到）：
- `> [!WARNING]` —— 「本软件不在任何应用商店，只从本仓库 Releases 下载；其它渠道的包不是作者发的」
- `> [!IMPORTANT]` —— 「首次安装需允许『未知来源』；仅支持 arm64-v8a 手机」
- `> [!TIP]` —— 「更新：软件内会提示，无需手动来下载」

理由：FAQ 节会长出一个"没人维护的答案列表"（本项目已被死文档坑过多次，见 `lessons.md` 第八节）；
而 alert 是**每句话都在正确的位置**。

## 7. 中文项目要不要中英双语

**四种流派都有真实样本**：

| 流派 | 样本 | 形态 |
|---|---|---|
| 单文件双语标题 | v2rayNG（63.5k） | `## Download / 下载`，中英各一行并排 |
| 多文件 + 顶部语言切换 | **rikkahub（上游）** | `README.md`（英）+ `README_ZH_CN.md` + `README_ZH_TW.md`，头部一行 `[简体中文](README_ZH_CN.md) \| [繁體中文](...) \| English` |
| 纯英文（作者是中国人） | Android-DataBackup（7.4k） | 0% 中文，另有 `## Translation` 节请人帮忙翻译 |
| 极简跳转 | legado（47.1k） | README 只有 **17 行**，正文是「相关链接」——文档全在别处 |

**推荐给东方无限：先纯中文单 README**，理由：
1. 用户群 100% 是中文用户（界面全中文、下载源是蓝奏云）；
2. 双语维护成本翻倍，而本项目**已有多次"文档跟不上代码"的记录**（`docs/plan/current-state.md` 抬头、
   `docs/handover/README.md` 版本号、`lessons.md` 十-2 描述的控制台守卫已被删）——再加一份文件 = 再加一处会腐烂的地方；
3. **等到真要对外（DFW-105 的目标）时**，再按 rikkahub 的形态加 `README_EN.md` + 顶部一行切换，
   不要在一个文件里塞双语（v2rayNG 的写法只适合 `Download / 下载` 这种两三个词的短标题，
   整段中英并排会让人**两种语言都读不下去**）。

## 8. 明确不要做的（看起来专业、实际没用）

1. **堆徽章**：commit 活跃度 / 代码质量分 / star 数 / last-commit / "Powered by"。
   证据：5 个最大项目有 0-3 个徽章（§1）。
2. **贴未经压缩的原图**：1080×2400 的手机截图直接 `![]()`，会把首页撑成几屏长。
   证据：真正展示截图的 8 个仓库里 6 个用带 `width=` 的 `<img>`（§2）。
3. **放自动生成的"Star History"曲线图**：rikkahub 有（`## ⭐ Star History`），
   但那是给"已经有人 star"的项目看热闹的；**新项目放它=首页有一块区域是 0**。
4. **写一堆"技术栈徽章 + 架构图 + CI 状态"**：开发者关心，**下载用户不关心**；
   这些放进 `docs/` 或 `CONTRIBUTING.md`，别占首页。
5. **超长 FAQ**：10 个里只有 2 个有，且都外链（§6）。
6. **双语逐段并排**：读不下去（§7）。
7. **`<details>` 折叠关键信息**：10 个里只有 termux 用（它内容极多）。
   普通用户**不会点开折叠**——重要的事（怎么装、能不能装）不能藏。
8. **把「致谢与第三方参考」放在首页显眼位**：本项目 `README.md:118` 有这个节，
   AGPL 义务**必须保留**，但它是"合规"不是"卖点"——建议保持在**页面靠后**（现在的位置就对了）。

## 9. 推荐结构（给东方无限的 9 段式）

> 顺序原则：**「这是什么 → 长什么样 → 怎么拿到 → 装得上吗 → 凭什么信你 → 还想要更多 → 合规」**

| # | 段落 | 放什么 | 证据依据 |
|---|---|---|---|
| 1 | **居中头部块** | 图标 `width=100` + `<h1>` 东方无限 + 一句标语（≤20 字）+ 3 个徽章（License/Release/Platform） | rikkahub 头部块（README:1-13） |
| 2 | **一句话定位** | 「安卓上的资源库 + AI 对话 + 下载器，免费、无广告、开源」 | v2rayNG 第三行定位句 |
| 3 | **截图区（当前最大缺口）** | 6 张手机图：`<p>` + `width="32%"` 三列两行（MaterialFiles 做法）；有平板/横屏图再补一张 `width=405` | §2-B / §2-A |
| 4 | **下载** | `## 下载` + 一行**裸 URL** 的 Releases 链接 + 版本/大小/arm64 说明 | v2rayNG `## Download`；`README.md:84-89` 已有雏形 |
| 5 | **安装（补"小白三句"）** | 允许未知来源 / 仅 arm64-v8a / 首次覆盖安装注意事项；用 `> [!IMPORTANT]` | §5、§6 |
| 6 | **五大板块功能介绍** | 保留现有内容（`README.md:25-76`），但**每节配一张对应截图**比纯文字有力 | 现状已有 5 节，只差图 |
| 7 | **安全与信任** | 签名校验 + 不在任何应用商店 + `> [!WARNING]` 山寨包提醒 + 服务端/权限说明 | rikkahub 的 fork 警告；Obtainium 的 `## Limitations` |
| 8 | **支持作者 / 构建 / 许可证 / 致谢** | 现状 `README.md:91-137` 基本可原样保留（顺序建议：支持作者 → 构建 → 许可证 → 致谢） | AGPL 义务 |
| 9 | （可选）**英文版** | `README_EN.md` + 顶部一行切换，**等真要对外时再做** | §7 |

**三个必须先修的现状问题**（都在门面最显眼的位置）：
1. Release 徽章显示 `test-20261004-02`（§0）——要么改成静态版本徽章，要么等 tag 规范后自然恢复；
2. 0 张截图 → 第 3 段整段缺失；
3. 下载节没有"允许未知来源"→ 普通用户第一步就会卡住。
