# 专题执行规程

> 这份规程服务于 [TASKS.md](TASKS.md) 的单专题节奏。它约束工作边界和证据质量，不把实现写死。

## 1. 接手一个专题

每次只接一个专题，例如 `T16 图标、头像与缓存可靠性`。接手时先读：

- 本专题在 `TASKS.md` 中的目标、现状、推荐方向和验收体验；
- 相关原始研究、代码和当前工作区状态；
- 相关风险条目及项目 `AGENTS.md`。

接手报告只需说明：当前状态、已有证据、未提交改动是否重叠、需要用户决定的产品边界。不要把旧行号、旧截图或旧代理结论当成当前事实。

## 2. 研究阶段：允许纠正计划

研究阶段只做只读调查、测试设计、样本采集和计划更新，不改业务源码、依赖、版本、远程配置或用户数据。

研究结果必须区分：

- **代码确认**：当前源代码、配置或构建产物直接证明的事实；
- **实测确认**：测试、真机、日志、网络响应或截图实际得到的结果；
- **推测/待验证**：合理线索，但尚未证明的因果或收益。

小模型不是机械施工者。它可以：

- 重新检查规划中的假设、范围、依赖和推荐方向；
- 用当前代码、实测或官方资料证明原建议不合适；
- 提出更小、更稳或更适合用户体验的替代方案；
- 发现专题需要拆出一个新的独立体验时，先记录并停在边界处。

纠偏时要写清「原建议是什么、证据是什么、改成什么、会影响哪些后续专题」。没有证据时只能写成待验证，不能把猜测升格为根因。

研究不要求把未来所有细节一次查完。只研究当前专题需要的深度；不要为了“完整”提前修改相邻专题的实现。

## 3. 用户批准关口

研究完成后，给用户一份短而完整的决定材料：

1. 要解决的用户体验和不做什么；
2. 当前事实、已知风险和仍不确定的地方；
3. 推荐方向，以及必要时 2–4 个可比较的产品/审美方案；
4. 预期验证方式、回退边界和可能影响的相邻功能；
5. 需要用户决定的事项，仅列真正改变产品、审美、成本、数据或不可逆范围的事项。

用户批准的是**这个专题的目标和范围**，不等于批准所有可能的实现方式、提交、推送、部署或公开发布。没有批准时保持研究状态。

普通实现参数（例如缓存期限、线程数、内部类名、测试顺序）由专题模型结合证据决定，不逐项丢给用户；若参数会改变用户承诺、成本、安全或数据处理，再停下来请用户决定。

## 4. 制作阶段

获得批准后：

- 只修改当前专题必要的文件和范围，保护已有未提交改动；
- 先建立能捕捉目标行为的最小验证，再改实现；不顺手重构、不升级无关依赖、不删源；
- 每个阶段保持可回退。发现计划错误、真实范围扩大、需要破坏性操作或触及另一个专题时，暂停并回报，不擅自跨过去；
- vendor 区遵守上游只读和 `rikkahub/PATCHES.md` 记录规则；宿主区遵守依赖、图标和动效红线。

“做成大任务”意味着本专题的正常流程、空态、等待、失败、恢复、兼容和可验证性都处理到足够好；不意味着把整个应用重写一遍。

## 5. 自测与证据

根据专题风险选择足够的验证层级，不机械执行一套固定命令：

- 逻辑变化：真实重跑相关 JVM/单元测试；先清理会导致假通过的测试任务；`UP-TO-DATE` 不是新证据；
- 编译/资源变化：跑与改动匹配的快速编译或构建，并记录真实结果；
- 用户可见或交互变化：用手机 release 包、截图、日志或可复现操作检查；只测手机，手表永久停止；
- 性能变化：保留同一设备、同一场景的帧时间分位、jank、内存、ANR/FATAL 等可比较数据，不写“感觉流畅”；
- 安全、密钥、更新或发布变化：做产物静态检查、负向路径和升级/回退检查；不输出任何凭据。

release 构建与 Debug 测试分开。真机验收使用 arm64 release 包，执行前核对当前 SDK、设备、ABI 和发版规范，不照抄历史地址或版本。

装机、启动和读日志可以按现行授权进行；卸载、清数据、`pm clear`、`adb shell rm`、覆盖备份、删除源或其他不可逆动作必须另行得到明确授权。用户正在使用手机时不做坐标点击。

## 6. 自测完成后的停工规则

小模型自测通过后，状态只能是**待用户测试**，必须停下来把以下内容交给用户：

- 本专题改了什么、没有改什么；
- 用户可以怎样实际操作，重点观察哪些正常和异常情况；
- 测试、构建、真机、截图和日志的真实证据；
- 已知未验证项、回退点和下一次只准备处理的反馈。

不能因为编译通过、代理说通过或自己看起来不错就自动进入下一个专题。用户反馈“不对、还差、某处退化”时，继续留在当前专题，先复现再调整；反馈涉及新的产品范围时，暂停并重新建立专题边界。

只有用户明确认可当前专题，且本专题的验收证据、风险和回退记录齐全，才标为完成。用户随后明确选择下一专题，才开始下一项。

## 7. 回报格式

每次回报按实际情况包含以下信息，缺项写“本专题不适用”，不要填空话：

- 专题和阶段：研究 / 待批准 / 制作 / 待用户测试 / 继续打磨 / 完成；
- 证据分类：代码确认、实测确认、推测与待验证；
- 改动文件和范围；
- 用户批准的目标与实际是否一致；
- 验证命令、真实结果、设备/截图/日志位置；
- 用户还需要测试什么；
- 风险、相邻专题影响和回退方式。

不要在回报中打印 key、Token、Cookie、签名密码或含敏感参数的完整 URL。计划文件只记录脱敏结论和可复查的本地路径。

## 8. 共同红线

- 未经用户批准不得开工改业务源码；本计划整理本身不构成开发授权。
- 不以旧计划、旧代理结论或规划者身份压过新证据；不把推测写成确定根因。
- 宿主不擅自引入第三方依赖；图标走现行 Phosphor SVG 转换；不恢复字体切换、SF Symbols 或已禁用的物理弹簧/`dynamicanimation`。
- 内置上游 AI key 不进 APK、不远程下发给客户端；服务端代理未就绪时不得带密钥占位发布；自定义渠道边界不能被误伤。服务端只允许经校验的 `http/https` 出站目标，拒绝 localhost、回环、私有和保留地址，凭据只从环境变量或密钥服务读取。
- 服务器、域名、付费服务、公开发布和删除/清理动作都不是默认批准项。清理前先列清单、体积和影响；不得触碰保险箱、交接 zip、已豁免系统组件或用户数据。
- 遵守 Mimosa 写入边界：源码/配置使用受控编辑工具，不用 Bash 写入；Git 按 hook 要求操作，不用被拦截的单文件 `git add` 方式。`local.properties` 不进 git/CI。
- 发版遵守 AGPL-3.0、RikkaHub 署名、ABI、签名、版本和 Release 命名规则；发布前读取 `.zcode/skills/dfwx-release/SKILL.md`。
