## 一、结论（先说最重要的）

| 问题 | 结论 |
|---|---|
| **这台服务器够用吗** | **性能够，但买它对项目是负收益**。2核2G 跑这几项负载余量 100 倍以上，但**大陆服务器会把你拖进 ICP 备案 + App 备案的义务**（1~20 工作日 + 后续公安备案），而 **Cloudflare 免费方案能覆盖全部需求且不需要备案**（前置：需自备一个域名，见 2.4 更正） |

| **当前资产实况** | 用户**目前没有服务器、也没有自己的域名**。`lanzouplus.nkbr.cc` 是**上游作者的域名**，与本项目无关 |

## 二、服务器评估

### 2.1 负载能力：2核2G 远远够用

| 负载 | 实际压力 | 判断 |
|---|---|---|
| JSON 配置接口 1 万次/天 | ≈0.12 请求/秒，响应 <10KB | 忽略不计（Nginx 单核可扛数万 QPS） |
| 反馈 POST 几百条/天 | ≈0.003 请求/秒 | 忽略不计 |
| APK 分发 100 次/天 ×75MB | ≈7.5GB/天 ≈225GB/月 | CPU/内存无压力；**瓶颈只在带宽和流量包** |
| 单人网页后台 | — | 忽略不计 |

**真正的风险不是算力，而是单点**：一个 75MB 下载跑满 200Mbps 时，同机的 JSON 接口会一起变慢。**APK 分发本就不该和 API 挤在同一台 2核2G 上。**

### 2.2 "200M 峰值带宽"是什么意思（关键坑）

阿里云官方口径：
- **出入共享**：200Mbps 是上行+下行的**总和上限**，不能同时跑满两个 200M
- **非业务承诺**：高峰期资源争抢时**会被限速并丢包**，不作为 SLA 承诺
- **生效时间**：购买后即刻限速，不是"流量用完才限速"
- 理论峰值 200Mbps ÷ 8 = **25MB/s**，但这是上限而非保底

对比：ECS 的"固定带宽"才是接近独享的保底带宽。峰值带宽适合"能容忍波动"的场景。

### 2.3 流量包（必须查清）

阿里云轻量服务器分两类套餐：
| 套餐显示 | 计费 | 动作 |
|---|---|---|
| **"无固定流量"** | 流量含在套餐费里，**无限用** | 促销款属于这类 |
| "每月流量"（如 1000GB） | 超出后按量付费，**大陆 0.8 元/GB**、香港 1 元/GB | 需监控 |

**购买后立即验证**：控制台 → 实例详情 → 服务器监控，**若出现"流量"指标 = 有固定配额**（会超额收费）；没有 = 不限流量。

按实际量级算：即使是最保守的 200GB/月套餐，也能支撑约 2700 次 75MB 下载/月。**流量不是瓶颈，备案才是。**

### 2.4 ICP 备案（决定性约束）

阿里云官方文档原文：
> "只要域名解析指向中国内地服务器，**无论使用标准端口（80、443）还是非标准端口（如 8080、8443），均须完成 ICP 备案**。"
> "域名用于内网穿透、**API 接口**等非网站场景时，只要解析指向中国内地服务器 IP，仍须完成 ICP 备案。"

→ **"用非标端口绕过备案"这条路已被官方明确堵死**，网上那些"唯一方法"的文章都过时了。

| 项目 | 说明 |
|---|---|
| 是否强制 | 是。不备案 → 阿里云自动检测拦截，返回未备案提示页 |
| 时间 | 阿里云初审 1~2 工作日 + 工信部短信核验 + 管局审核 **1~20 工作日** |
| 费用 | 备案免费；但需**购买时长 ≥3 个月**的大陆服务器才能申请备案服务码 |
| 附加义务 | 备案后 **30 天内必须完成公安联网备案** |
| **App 备案** | 工信部要求：服务器在境内、需联网的 App 需备案。2024 年 4 月起监督检查，未备案面临停止接入/下架 |

**替代方案对比**：

| 方案 | 备案 | 评价 |
|---|---|---|
| 香港/海外服务器 | **不需要** | 可行，延迟略高 |
| **Cloudflare Workers/Pages** | 不需要 | **最优**：免备案、免费、自带全球 CDN 和 DDoS 防护 |
| 阿里云 OSS 用系统默认域名 | 不需要 | 域名丑、无自定义域名；**绑自定义域名就必须备案** |
| GitHub raw 直连 | 不需要 | **不可行**：`raw.githubusercontent.com` 在大陆被墙 |

**⚠️ 重要更正（2026-09-26 二次核实）**：本文档早先版本曾写"现有的 `lanzouplus.nkbr.cc` 已经在 Cloudflare 上、你已经在用最省事的方案了"——**这句话是错的，已删除**。

核实结果：`nkbr.cc` 是**上游作者 nekobyran 的域名**（包名 `cc.nkbr.lanzouplus` 即其缩写），其 `latest.json` 返回的是"LanzouPlus 1.4.8 官方公开版"，下载地址指向 `github.com/nekobyran/lanzouplus`。**它跟本项目无关，用户既没有服务器也没有域名。**

**因此 Cloudflare 方案的前置条件是**（比原判断多两步，需用户投入）：
1. **先有一个自己的域名**（约 ¥30~80/年，Cloudflare Registrar / Namesilo / 阿里云均可）
2. 把该域名的 NS 改到 Cloudflare（免费账号），等待生效

**在没有域名之前**，唯一零成本可用的通道是 **GitHub Releases**（本项目已在用，更新检查修复后即可工作）。域名与 Worker 是"远程公告/远程源列表/失效反馈收集"这些增强功能的前置条件，不是当前阻塞项。

### 2.5 48 元/年这个价格

阿里云官方真实促销价：**2核2G/200M峰值/40G ESSD/不限流量 = 秒杀 38 元/年**（每天 10:00、15:00 限量）、**优惠价 68 元/年**（官网标价约 459 元/年）。

所以 **48 元落在 38~68 元区间，价格本身合理**，很可能是黄牛抢到 38 元名额后加价转卖。

**但代购模式有三个硬风险**：
1. **无法备案（决定性）**：如果是"用他的账号给你用"，服务器实名主体是他，**你无法以自己的名义备案**；他随时能通过阿里云账号找回控制权。
2. **续费陷阱**：促销价仅首年，第 2 年按官网价（约 459 元）或老用户优惠（约 99 元），**不会还是 48 元**。
3. **活动资格**：38/68 元明确"仅限阿里云新用户"。若你的账号已买过云产品，**自己下单没有这个价**——这也是代购存在的土壤。阿里云官方已就"五折代付"等黑产发过风险警示（封号、数据丢失、欠费追索）。

**建议**：如果真想买，**用自己的实名账号去阿里云官网**走官方活动。别走闲鱼代购——为省 20 块钱换来一个不能备案、随时可能被收回的服务器，不值。

## 三、后台架构方案

### 3.1 五种方案对比

| 方案 | 成本 | 备案 | 运维 | 抗压 | 适配 |

| C. 轻量服务器 + 动态后端 | 48元+ | **必须** | **高** | 中 | ❌ 一个人维护太痛苦 |
| **D. Cloudflare Workers + KV + R2** | **0** | **不需** | 低 | **极强** | ✅ **推荐** |
| E. 阿里云 OSS + CDN | 按量 | 绑自定义域名**必须** | 低 | 强 | APK 分发备选 |

**Cloudflare 免费额度**（官方文档）：
| 资源 | 免费额度 | 你的用量 | 余量 |
|---|---|---|---|
| Workers 请求 | **10 万次/天** | 1 万/天 | 10 倍 |
| KV 读 | 10 万次/天 | 1 万/天 | 10 倍 |
| KV 写 | **1000 次/天** | 几百次/天 | 勉强够（反馈量大需换 D1） |
| **静态资源请求** | **免费且无限** | 配置下发全走这里 | 无限 |
| R2 存储/出口 | 10GB / **出口免费** | APK 分发 | ✅ 零成本 |

### 3.2 推荐组合（混合架构）

```
配置源（唯一真相）：GitHub 仓库里的 config.json
   │  （你直接改文件、手机也能改、有版本历史和回滚）
   ↓
Cloudflare Workers / Pages
   ├─ 静态资产：公告、源列表、版本信息（免费无限请求，全球 CDN）
   ├─ /api/feedback → KV 或 D1（收集用户反馈）
   └─ /api/ai-proxy → 服务端注入上游密钥（见安全章）
   ↓
APK 分发：GitHub Releases（已有）+ Cloudflare R2 镜像
后台界面：GitHub 网页端改 JSON（零开发）或一个静态 admin 页面
```

对应五项需求：
| 需求 | 实现 | 成本 |
|---|---|---|
| 远程公告 | 静态 `announce.json`，App 拉取 | 0 |
| 远程更新 | **先修 bug**（见 T6B），再让端点指向自己的仓库 | 0 |
| 资源库列表下发 | 静态 `sources.json`，App 比对版本号覆盖内置 84 源 | 0 |
| 失效反馈收集 | Workers POST → KV/D1，写个小页面看 | 0 |
| **API 密钥下发** | ❌ **不要做**，改服务端代理（见下） | 0 |

**关键改造点**：`UpdateClient.java` 的 host 白名单是硬编码的。新增远程配置端点时**必须同步扩展白名单**，否则会被"更新地址不受信任"拦掉。**这个校验逻辑本身写得很好，别删。**

### 3.3 后台管理界面怎么最省事

| 形态 | 评价 |
|---|---|
| **直接改 GitHub 仓库里的 JSON** | ✅ **最省事**。零开发、有版本历史、有回滚、手机浏览器就能改。缺点：改完要等 CDN 缓存（几分钟） |
| Telegram Bot | 体验好，但**大陆需要代理才能用** |
| 自建网页后台 | 要额外开发+维护，对"一个人+4 项需求"属于过度工程 |

**现成开源项目**（star 数为实测，2026-09-26）：PocketBase（61.2k，单文件后端+自带管理后台，**若要买服务器首选它**）、NocoDB（65.1k）、Supabase（110.8k）、Directus（38.0k）、Flagsmith（6.6k）、GrowthBook（8.4k）、Unleash（13.8k）。

**建议：以上都不用。** 你的场景（1 个人、4 项需求、极低成本）用 **GitHub 仓库 JSON + Cloudflare Worker** 就够，代码量约 100 行，比部署任何一个开源后台都简单。

## 四、安全设计（诚实版）

### 4.1 "内置 API 密钥远程下发"——不能解决拆包，直说

**结论：不能。这个思路从根上是错的。**

根本原因：**客户端必须能读到密钥才能用它。攻击者能拿到 App 的一切，你就无法对他保密。** 无论把密钥放在：
- 代码里 → 反编译/搜字符串
- `res/values` → 解包 `resources.arsc`
- **远程下发 → 抓包直接拿到**（连反编译都不用，装个 mitmproxy 就行）
- 加密存储 → hook 解密函数拿明文（Frida）

**远程下发唯一的好处是"可轮换"**：泄露后你能换掉。但代价是**你得持续不断地换**——因为密钥会一直泄露。这不叫解决问题。

**而且项目已经有这个问题**：`SECURITY.md` 里自己写了"内置默认 AI 渠道的 Key 以资源形式打包在 APK 内（服务端已按共享 Key 设定限额）"。**好消息是：现在的应对方式（共享 Key + 服务端限额）方向是对的**，这是"密钥必然泄露"前提下的正确降级方案。

**业界公认的正确做法**（Android 官方文档）：
> "使用 API 服务提供的安全身份验证、客户端验证和会话控制，并考虑**使用动态令牌来代替静态密钥**。确保令牌在合理的时间内过期（通常为 1 小时）。"

| 方案 | 做法 | 效果 |
|---|---|---|
| **推荐：服务端代理** | 上游 AI 密钥**只存在 Cloudflare Worker 的环境变量里，永不下发**。App 调 `你的域名/api/ai-proxy`，Worker 在服务端把密钥加到请求头转发 | ✅ 上游密钥永不暴露。App 侧只持有一个"可限流、可吊销"的 App Token |
| 短期令牌 | Worker 签发 1 小时有效期的短令牌 | 提高攻击成本，但 Token 仍可被抓包 |
| 保持现状 | 内置 Key + 服务端限额 | 可接受，但拆包就能白嫖额度 |

**你要的"后台换密钥"可以满足**，但正确形态是：**在 Cloudflare 后台改 Worker 的环境变量**（不是下发给 App）。这样换密钥立即生效、无需发版、App 侧零改动——正好实现了"远程更换、避免拆包泄露"，只是密钥不下发而已。

### 4.2 通信加固手段的能力边界

| 手段 | 能防住 | 防不住 |
|---|---|---|
| 请求签名（HMAC） | 路人改包、重放 | **密钥在客户端 → 可被提取** |
| 时间戳 + nonce | ✅ **重放攻击**（真有效） | 不影响伪造 |
| 证书固定（Pinning） | 装了自定义 CA 的中间人抓包 | ❌ **root 设备 + Frida 一行命令绕过** |
| 反调试/反 Root | 提高门槛 | 只是提高门槛，不是墙 |

**结论**：这些手段的价值是"**提高攻击成本，挡住 99% 的普通用户**"。值得做的是**时间戳+nonce 防重放**（成本低、真有效）和**HTTPS 强制**；pinning 可以做但别指望它。

### 4.3 APK 完整性

| 方案 | 可用性 |
|---|---|
| **Play Integrity API** | ❌ **国内不可用**（只支持 Google 认证设备 + 需经 Google Play 分发） |
| **自签名校验** | ✅ **项目已做，而且做得对**。`verifyUpdateApk()` 校验 SHA-256 + 签名一致性，能防"更新通道被投毒"。但防不住别人独立重打包后另找渠道分发 |
| 代码混淆/加固 | 提高门槛，开源项目意义有限 |

**诚实结论**：开源 App 无法阻止别人重打包。能做的是：① 保证**你的更新通道**安全（已做到）② 在官网/README 公示官方 SHA-256 与签名指纹（`SECURITY.md` 已做）③ 用户侧靠"同签名才能覆盖安装"这道系统防线。

### 方案二：买服务器（如果还是想买）

**先决条件**：必须用**自己的实名阿里云账号**在**官网**下单，不要闲鱼代购。

| 步骤 | 操作 | 坑 |
