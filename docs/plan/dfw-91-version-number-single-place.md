# DFW-91：版本号只保留一处（并且不用手改）

> 用户原话（2026-10-01）：
> **「版本号的话，你要是改一堆地方的话……可能会漏掉。你就找一个地方放版本号吧，
> 在检查更新四个字右侧放着版本号。然后关于东方无限底部的和其他地方显示版本号的地方，
> 你都给我删除，优化掉。不然的话，你每次更新都得改一堆地方。」**

## 1. 用户真正在意的是"维护负担"，不是"版本号好看"

追问后用户说得很直白：「**我主要是想减轻你的维护负担，别忘记改某些地方的版本号**」。
所以这一卡要解决的是**漏改**，不是排版。

## 2. 改前：版本号散在 4 处

| 位置 | 性质 |
|---|---|
| 设置页「检查更新 · 当前 1.0.x」 | 用户可见（保留，挪到右侧） |
| 「关于东方无限」页底部 `东方无限  1.0.x` | 用户可见 → **删** |
| 维护页底部 `东方无限 1.0.x` | 用户可见 + **连点 7 次的后门** → 去掉版本号、**后门保留** |
| 「已是最新版本（1.0.x）」 | 用户可见 → **删**（版本号就在上面一行） |

另有 4 处**非 UI** 用途（崩溃报告文件名、崩溃报告邮件主题、`UpdateClient.check` 参数），
它们不产生维护负担，保留。

## 3. 改后：用户可见的版本号只剩 1 处

`settingsAction(R.drawable.ic_refresh,"检查更新",BuildConfig.VERSION_NAME,v->manualCheckForUpdates())`
—— 新增了一个带**右侧说明文字**的 `settingsAction` 重载。

## 4. 更关键的一半：让"漏改"物理上不可能

### 4.1 代码里只有一个数字
`app/build.gradle.kts` 以前要改**两行**（`10023` 和 `"1.0.23"`），改漏一行
`VersionSchemeJvmTest` 立刻变红；而改漏 `versionCode` 的后果最阴——用户永远收不到更新，
界面上完全看不出来。现在：

```kotlin
val buildCode = 10023
versionCode = buildCode
versionName = "${buildCode / 10000}.${(buildCode / 100) % 100}.${buildCode % 100}"
```

### 4.2 事实页从"报错"改成"自动写入"
`tools/release.sh` 原来只检查 `docs/plan/current-state.md` 有没有跟上，没跟上就 `fail`。
**靠人记得改文档不可靠** —— 上一个窗口就真的漏过一次，是 `DocTimelinessJvmTest`
变红才发现的。现在改成 sed 自动写入，想漏都漏不掉。

### 4.3 `build` 强制先跑 `verify`（本次发现的最严重问题）
`release.sh` 的 `verify` 与 `build` 原来是**两个互不相干的子命令**：门禁只在 `verify` 里，
`build` 直接出包。**v1.0.15「带红门禁发布」就是这么发生的。**
现在 `cmd_build` 开头直接调用 `cmd_verify`。

## 5. 维护页后门（用户亲自定的处理方式）

- 那行文字**不再显示版本号**，只写「东方无限」
- **点击零反馈**（不弹提示、不震动、不变色）—— 有反馈就会被普通用户发现
- 第 7 次点击后：正常放行 + 弹出说明。文案是用户 2026-10-01 亲自写的，一字未改：
  > 测试后门已开启，这是我刻意留下的备用测试通道，如果你是用户，还请小心使用，
  > 因为当我开启了维护模式，那就说明该软件或许出现了什么问题或者是故障与异常，我无法保障你的安全。

用**对话框**而不是顶部通知条：通知条正文上限 4 行，这段 80 多字在窄屏上会被截断，
而**被截掉的正好是最后那句"我无法保障你的安全"** —— 那才是要让人看见的部分。

## 6. 本次顺带修掉的 3 个潜伏 bug（都在"只在出错分支才执行"的代码里）

shell 脚本里 `$变量` 后面**紧跟中文全角字符**时，bash 会把中文字节吞进变量名，
报 `name?: unbound variable`：

| 文件 | 原写法 | 后果 |
|---|---|---|
| `tools/release.sh:78` | `$name（自动写入）` | **本次实际踩到**，verify 直接崩 |
| `tools/ci-gate.sh:113` | `$bad（...` | 只在门禁报错时才执行 → 出错时反而崩 |
| `tools/dfwx-publish-apk.sh:40` | `$REMOTE_SHA）` | 只在 sha256 不一致时才执行 → 校验失败时反而崩 |

一律改成 `${变量}`，并加守卫 `shellScriptsNeverGlueAVariableToChineseText` 防复发。

  `release.sh` 退回"只报错不自动改" → 红
- 4 条**断言旧行为**的老测试按新行为更新（`BrandCreditsJvmTest` /

## 8. 前车之鉴

- **别用 `\g<1>` 写 BSD sed 的替换** —— 本次实测把 `current-state.md` 写坏成
  `g<1>10022g<2>1.0.22g<3>（...`，靠备份还原。BSD sed 用 `\1`。
- **管道会吃掉退出码**：`bash gate.sh unit | tail -4 && build` 里的 `&&` 看到的是
  `tail` 的退出码 —— 这正是本次差点又"带红门禁发版"的原因。要么不加管道，要么 `set -o pipefail`。
